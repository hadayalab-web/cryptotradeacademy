# X投稿の重複・ゴミ投稿・空返信の修正（2026-02-01）

## 概要

Xプロフィールで観測された「意図しない挙動」を分析し、以下を修正しました。

- **重複投稿**: 同一コンテンツ・同一時間帯の重複
- **「テスト」投稿**: 本番で「テスト」単体の投稿が流れる
- **空/グレー返信**: ユーザーリプライ自動返信の重複・空投稿の可能性

---

## 原因分析

### 1. ユーザーリプライ自動返信の重複（userReplyHandler）

- **場所**: `services/x/userReplyHandler.js`
- **問題**: 「処理済み」マークを **setTimeout のコールバック内** でしか設定しておらず、`results` は非同期で増えるため、**関数を抜ける時点では常に `results.length === 0`** だった。
- **結果**: `x:user_replies:${mainTweetId}` がほぼ設定されず、同じメインツイートに対して **x-post-free-report が複数回走るたびに handleUserReplies が再実行** され、同じリプライに何度も自動返信する可能性があった。
- **補足**: 返信は 5〜15 分のランダム遅延（setTimeout）で送るため、その間に同じ Cron が再度実行されると重複が発生しやすい。

### 2. 「テスト」単体投稿

- **問題**: 本文が「テスト」や「test」のみの投稿が本番に流れていた。コード内に「テスト」を投稿する箇所は見つからず、手動テストや別スクリプト・環境の誤実行の可能性が高い。
- **対策**: 投稿・返信の共通レイヤー（`services/x/client.js`）で、本文が「テスト」「test」のみの場合は **常にエラー** とするガードを追加し、今後同様の誤投稿を防ぐ。

### 3. 空返信・グレー枠

- **想定**: 空または極端に短いテキストで `replyToTweet` が呼ばれた場合、X側で空/表示されない返信になる可能性。既に `replyToTweet` では空文字で `throw new Error("Reply text is required")` を投げている。
- **補足**: スクショの「グレー枠」は、削除された元ツイートへの返信や表示の不具合の可能性もある。

### 4. 重複投稿（同一画像・同一リンクカード）

- **想定原因**:
  - **Cron の二重起動**: Vercel Cron が短時間に複数回同じ API を叩く場合がある。
  - **同一レポートの複数回実行**: `x-post-free-report` が同じ「枠」で複数回呼ばれ、日次/時間帯の重複防止が不十分だと同一内容が複数回投稿される。
- **今回の対応**: ユーザーリプライ処理の「処理済み」を **処理開始直後** にマークするように変更し、少なくとも **同じメインツイートへの自動返信の重複** は抑止。

---

## 実施した修正

### 1. `services/x/userReplyHandler.js`

- **処理済みマークのタイミング変更**
  - **変更前**: ループと setTimeout の後、`if (kv && results.length > 0)` のときだけ `x:user_replies:${mainTweetId}` を設定。  
    → `results` は setTimeout 内でしか増えないため、**ほぼ常に設定されていなかった**。
  - **変更後**: リプライ取得直後（`getTweetReplies` の後）、**ループの前** に `x:user_replies:${mainTweetId}` を即時設定（有効期限 7 日）。
- **効果**: 同じ `mainTweetId` に対して 2 回目以降の `handleUserReplies` は「既に処理済み」と判定され、自動返信の二重送信を防止。
- **ログ**: 「処理完了をマーク」のブロックを削除し、代わりに「Scheduled N user replies for tweet …」のログに統一。

### 2. `services/x/client.js`

- **テスト投稿ガードの追加**
  - 新規関数 `rejectTestOrTrashPost(text, context)` を追加。
  - 本文を `trim()` した結果が **「テスト」または「test」（前後の空白のみ可）** の場合に `Error` を throw。
  - `postTweet` と `replyToTweet` の先頭で、空チェックの直後にこのガードを実行。
- **効果**: 本番・ステージング問わず、「テスト」「test」のみの投稿・返信は API 層でブロック。テストは `X_POSTING_DRY_RUN=true` で行う想定をドキュメント化。

## 運用上の注意

1. **既に流れた「テスト」投稿**  
   過去の「テスト」投稿は手動で削除するか、X の管理画面で対応してください。今回の修正は **今後の投稿のみ** ブロックします。

2. **重複投稿の既存分**  
   既にタイムラインに出ている重複投稿も、必要に応じて手動で削除してください。今回の修正で **新規のユーザーリプライ自動返信の重複** は抑止されます。

3. **Cron の二重起動**  
   Vercel の Cron が同一分に複数回同じ API を叩く場合、**x-post-free-report 本体の重複実行** は今回の変更では直接は防いでいません。必要であれば、x-post-free-report 側に「今日・この時間帯・言語」単位の KV キーで idempotency を入れる検討を推奨します。

4. **テスト投稿のやり方**  
   実際に X に投稿したい場合は、本文に「テスト」だけではなく、例えば「テスト投稿 2026-02-01」のように別の文言を入れるか、`X_POSTING_DRY_RUN=true` でドライラン運用してください。

## 今後の確認推奨

- Vercel ログで `/api/x-post-free-report` と `/api/x-webhook` の呼び出し頻度・時刻を確認し、Cron の二重起動がないか監視する。
- 同一「日付・時間帯・言語」で x-post-free-report が複数回実行されないよう、KV 等を使った idempotency キーの導入を検討する。
