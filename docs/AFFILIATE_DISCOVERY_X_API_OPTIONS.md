# アフィリエイター発見の再考：Search recent Posts 以外の X API 活用

**前提**: Search recent Posts にこだわりすぎず、[X Developer Platform](https://docs.x.com/overview) の複数リソースを組み合わせて「アフィリエイター候補の X ユーザー」を見つける。

---

## 0. ターゲットの枠組み（発見のゴール）

システムで「見つけてブックマークする」対象は、次の **3 条件** で揃える（運用指示）。

| 条件 | 意味 |
|------|------|
| **アフィリエイターとして活動中** | すでにアフィリエイト／紹介／プロモをやっている（検索クエリで発見）。 |
| **案件を募集中である** | 新規案件・コラボ・DM 歓迎のニュアンス（「open to collab」「DM for business」等）。検索で除外しない。 |
| **フォロワー100人以上** | フォロワー数が 100 未満の著者は候補から外す。 |

**6言語圏**（EN / ES / PT / AR / JA / KO）でこの手掛かりで候補を見つけ、該当投稿をブックマークする。あなたは X のブックマーク一覧から手動でフォロー・いいね・リプライ・DM できる。

- **システムの役割**: 上記 3 条件・6言語で候補を発見し、ブックマーク（またはキュー）で「誰にリプライ／DM するか」の一覧を渡す。
- **人の役割**: その一覧を見ながら、X 上で手動でリプライ・DM を送る。

## 1. 発見に使える X API リソースと単価（抜粋）

| リソース | 単価 | 用途イメージ |
|----------|------|-----------------------------|
| **投稿: 読み取り** (Posts Read) | $0.005 / リソース | キーワード検索で「誰が投稿したか」を取得。現行の主力。 |
| **ユーザー: 読み取り** (Users Read) | $0.010 / リソース | ユーザーIDから profile / description を取得。プロフィールでアフィリ意図を判定。 |
| **リスト: 読み取り** (Lists Read) | $0.005 / リソース | リストのメンバー一覧を取得。キュレーション済みリストなら質の高い候補。 |
| **フォロー/フォロワー: 読み取り** (Follows/Followers Read) | $0.010 / リソース | シードアカウントのフォロワー/フォロー一覧 → ユーザー Read で絞り込み。 |
| **コミュニティ: 読み取り** (Communities Read) | $0.005 / リソース | コミュニティメンバー・投稿から候補を発見。 |
| **スペース: 読み取り** (Spaces Read) | $0.005 / リソース | スペースのホスト/参加者から候補を発見。 |
| **トレンド: 読み取り** (Trends Read) | $0.010 / リソース | トレンドは「誰を探すか」のテーマ決めに利用。 |

※ 最新の単価・制限は [X API Pricing](https://docs.x.com/x-api/getting-started/pricing) で確認すること。

## 2. 発見パターン比較

### A. 現行：Search recent Posts のみ

- **流れ**: クエリ（例: "affiliate link" OR "promo code"）→ 投稿取得 → author_id 抽出 → ユーザーは expansions で取得。
- **長所**: 投稿テキストで「いまアフィリ系を発信している人」を直接拾える。
- **短所**: クエリ設計に依存、ノイズや 403 が多いとコスト対効果が悪い。**突破口がこれだけ**だと行き詰まる。

### B. シードアカウントのフォロワー/フォロー

- **流れ**: シード（既知のアフィリエイター or 自アカウントのフォロー）を数件指定 → **Followers/Following API** で user_id 一覧取得 → **Users Read** で description 等を取得 → description に "affiliate" / "referral" / "link in bio" 等が含まれる人を候補にする。
- **単価**: Followers Read $0.010/件 + Users Read $0.010/件。例: シード1人あたり 500 フォロワー取得 → 500 + 500 = 1000 リソース → $10。投稿検索を一切使わない。
- **長所**: 検索クエリ不要。すでに「アフィリっぽい人の輪」にいるユーザーを拾いやすい。リストが静的に用意できる。
- **短所**: シードリストの質に依存。フォロワー数が多いとページングで Read が増える。

### C. リストのメンバーを読む

- **流れ**: 自分または他者が作った **リスト**（例: "Crypto affiliates", "Trading influencers"）の ID を指定 → **Lists Read** でメンバー一覧取得 → **Users Read** でプロフィール取得 → description で絞り込み。
- **単価**: Lists Read $0.005/リソース、Users Read $0.010/リソース。リストがキュレーション済みなら、投稿検索より少ない Read で候補を確保できる。
- **長所**: リストが良質ならノイズが少ない。検索窓やキーワードに依存しない。
- **短所**: 良いリストを誰かが作ってメンテしている必要がある。

### D. コミュニティ / スペース

- **流れ**: クリプト・副業・アフィリ系の **コミュニティ** or **スペース** に参加者/ホストがいる → その ID を **Users Read** で取得 → description で絞り込み。
- **単価**: Communities/Spaces Read $0.005 + Users Read $0.010。
- **長所**: テーマがはっきりしているので、意図が近い候補が集まりやすい。
- **短所**: コミュニティ/スペースの ID や取得方法の把握が必要。

### E. ハイブリッド（投稿検索 + 他リソース）

- **流れ**: 
  - まず **Search recent Posts** で少なめに取得（1クエリ・1ページ程度）→ 候補をキューに追加。
  - 並行または別 Cron で **シードのフォロワー** or **リストメンバー** を取得 → 同じキューにマージし、重複は author_id で除外。
- **長所**: 検索だけに依存せず、フォロワー/リストで「検索では出てこないが質の高い候補」を補える。
- **短所**: 実装と運用が少し複雑になる。

## 3. コスト感の目安（月あたりのイメージ）

- **現行（検索のみ）**: 1言語あたり 1 ページ × 4h ごと → 約 180 回/月。1回 100 投稿 + 100 ユーザー → 約 $90（投稿）+ $180（ユーザー）= $270/言語。6言語で約 $1,620（検索主体の場合）。
- **シード 5 人 × フォロワー 300 人**: フォロワー 1,500 + Users 1,500 = 3,000 リソース → $30。月1回なら $30、週1回でも $120 程度。**検索を使わずに**候補を補充できる。
- **リスト 1 本 500 メンバー**: Lists 500 + Users 500 = 2,500 リソース → $7.5 + $5 = $12.5 程度。リストを複数・複数回読むと増える。

→ **Search だけに頼らず、フォロワー/リストで「安く・少ない Read」の候補を足す**と、単価と発見の幅のバランスが良くなる。

## 4. 実装の方向性（提案）

1. **現行を維持**: Search recent Posts によるリスト取得（en-list / regions-list）はそのまま「ひとつの入口」として残す。
2. **シードフォロワー発見を追加（推奨）**:  
   - 設定で「シードユーザー ID（または @screen_name）」を数件指定。  
   - Cron または手動で「シードのフォロワーを N 件取得 → Users Read で description 取得 → キーワードマッチしたらキューに追加」する API を 1 本用意。  
   - 既存の `affiliate_recruit:queue:*` にマージし、重複は author_id で除外。
3. **リスト発見の追加（任意）**:  
   - リスト ID を設定に持たせ、「リストメンバー取得 → Users Read → 絞り込み → キューに追加」する API を 1 本。  
   - リストは手動でキュレーションしておく想定。
4. **発見チャネルを「検索 / フォロワー / リスト」で選べるようにする**:  
   - 同じキューに流し込むので、手動 DM するときは「どこから来た候補か」を `detected_via` などで区別できるとよい。

## 5. まとめ

| 発見方法 | 主な API | コスト目安 | 備考 |
|----------|----------|------------|------|
| 投稿検索（現行） | Posts Read + Users (expansions) | 高め | 突破口の一つだが、これだけに依存しない。 |
| シードのフォロワー | Followers Read + Users Read | 中〜低 | シードさえ良ければ質の高い候補。実装優先度◎。 |
| リストメンバー | Lists Read + Users Read | 低め | 良いリストがあればコスパ良い。 |
| コミュニティ/スペース | Communities/Spaces Read + Users Read | 要調査 | テーマが合えば有効。 |

**結論**: Search recent Posts は「ひとつの突破口」として残しつつ、**シードのフォロワー**（と必要ならリスト）を追加すると、X ユーザーからアフィリエイターを見つける方法が増え、コストと発見の質の選択肢が広がる。

## 6. ブックマーク一覧で手動フォロー・リプライ・DM

発見した「アフィリっぽい投稿」を **X のブックマークに追加** し、あなたがブックマーク一覧から片っ端からフォロー・いいね・リプライ・DM する運用。

- **API**: `GET/POST /api/affiliate-recruit-bookmark?lang=en`（要 CRON_SECRET。`?dryRun=1` で検索のみ）
- **流れ**: 指定言語でアフィリ検索 1 ページ → ヒットした投稿の tweet_id を認証ユーザーのブックマークに追加（1ランあたり最大 10 件・X 制限 50/15 分に合わせて調整可）
- **あなた**: X のブックマークを開く → 各投稿から作者をフォロー・いいね・リプライ・DM

環境変数: `AFFILIATE_BOOKMARK_CAP_PER_RUN`（既定 10）、`AFFILIATE_BOOKMARK_DELAY_MS`（既定 2000）。ブックマーク作成は X API で $0.005/リクエスト。
