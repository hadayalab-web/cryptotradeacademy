# リクルートDM: Read 抑制 × Create 最大化の設計

## 前提

- **Read**（X API ダッシュボード）= **検索条件数**（実行した search クエリの本数）
- **DM Interaction Create** = 送信成功数（課金対象）
- **目標**: Read を抑え、Create を伸ばす → **コスパ向上**

---

## ロジック

| 現在 | 狙い |
|------|------|
| キーワードをバケット分割 → **複数クエリ**（例: 6 条件） | **1 言語あたり 1 クエリ**（Read 1） |
| 1 クエリあたり 3 ページ取得 | 1 クエリで **多ページ取得**（例: 8–10 ページ） |
| 候補数 = 全クエリのツイートを合わせて重複除く | 候補数 = **1 クエリ × 多ページ** で十分な母数確保 |

- **Read を減らす**: クエリを 1 本にまとめる（全キーワードを 1 つの OR 条件に収める。文字数制限まで）。
- **候補を増やす**: クエリ数は 1 のまま、**ページ数だけ増やす**。Read は増えず、取得ツイート数が増える → ユニーク作者数（候補数）増加 → 送信試行数・成功数（Create）を増やしやすい。

---

## 設計方針

1. **1 言語 1 クエリ**: `buildSearchQueries(lang)` で、全キーワードを 1 本の OR クエリにまとめる。文字数制限（例: 480）を超える場合は末尾からキーワードを削って収める。**デフォルトで有効**（`AFFILIATE_RECRUIT_SINGLE_QUERY=0` で従来のバケット分割に戻す）。
2. **多ページ取得**: デフォルトの `SEARCH_PAGES_PER_BUCKET` を 3 → **8** に変更。1 クエリから 8 ページ取得（例: 8 × 50 = 400 ツイート → 重複除いた作者数が候補プール）。`BUZZWEAVE_SEARCH_PAGES_PER_BUCKET` で上書き可。
3. **AR の from: クエリ**: 単一クエリモードではキーワード 1 本のみ。AR で from: を使う場合は従来モード（`AFFILIATE_RECRUIT_SINGLE_QUERY=0`）で Read 2 になり得る。

---

## 期待効果

- **Before**: Read 6、候補 8、Create 3
- **After**: Read 1、候補 数十〜100+、Create 6 に届きやすく

→ **Read 単価あたりの Create 数が増える = コスパ向上**
