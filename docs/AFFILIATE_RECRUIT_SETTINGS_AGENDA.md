## 目標

- **1リクルートDMあたりのコストを $0.1 未満** にする。これが達成できれば、X のリミット **15 DM/分** に合わせて数多く撃ち込める。現状は約 $0.18・Read/DM 約 1.2。#1〜#15 で候補の取り方・並び順・上限類を見直し済み。
- **唯一の必須**: 送信成功目標 **10**（1 ランあたり 10 送信成功をマスト）。それ以外の設定値（時刻・スロット数・係数など）は運用指示や目安でよく、どうでもよい。
- **スコアのウェイト・係数**: 並び順・除外に使っておらず因果が薄いため、計算から削除。非除外時は固定 score=50・breakdown={}。stats/response 用の目安のみ。

### #17 SEARCH_QUERY_BUCKET_SIZE — 課題感・改善案

**課題感**

1. **数値 3 に根拠がない**  
   バケット分割時の「1 クエリあたりのキーワード数」として 3 が使われているが、なぜ 3 なのかがコード・ドキュメントにない。

2. **デフォルト運用では未使用**  
   `AFFILIATE_RECRUIT_SINGLE_QUERY` のデフォルトは有効（`!== "0"`）のため、通常は **1 言語 1 クエリ**（`buildSearchQueriesSingle`）が使われ、`SEARCH_QUERY_BUCKET_SIZE` は **参照されない**。効くのは `AFFILIATE_RECRUIT_SINGLE_QUERY=0` の従来モードのみ。

3. **従来モードでは run が 1 クエリ目だけ使う**  
   run は `buildSearchQueries(lang)` の **先頭 1 クエリだけ** を検索に使う。従来モードだと「先頭バケット＝先頭 3 キーワードのみ」で検索することになり、他キーワードは実質使われず、候補の幅が狭い。Read は 1 回で済むが、キーワードカバーは最小。

**改善案**

| 案 | 内容 |
|----|------|
| **A. 根拠を明記して 3 のまま** | 「従来モード（SINGLE_QUERY=0）時のみ使用。1 クエリが MAX_CHARS(480) を超えないようバケット分割するときのサイズ。3 は 1 クエリに収まりやすい目安。通常運用は 1 言語 1 クエリのため未使用」とコードまたは AUDIT に書く。値は変更しない。 |
| **B. 従来モードを廃止** | 1 言語 1 クエリで Read 最小化・$0.1/DM に寄せているため、バケット分割モードを削除する。その場合 BUCKET_SIZE 定数も削除。必要なら AR の from: だけ別経路で対応。 |
| **C. 値の変更は計測してから** | 従来モードを残すなら、3 → 5 などにすると 1 クエリ目に含まれるキーワードは増えるが、クエリ長オーバーで末尾削りが増える。クエリ数・ヒット数・文字数制限のトレードオフを計測してから決める。 |

**推奨**: 現状デフォルトで 1 言語 1 クエリなら **A（根拠を明記して 3 のまま）** で十分。従来モードを今後も使う予定がなければ **B（廃止）** でコードを簡素化できる。  
→ **案 A で完了**。コード・AUDIT に根拠を追記し、値は 3 のまま。

### #18 EN_RECRUIT_HOURS — 課題感・改善案

**役割**

- EN スロットが **いつ実行されるか** を決める。`utcHour` がこの配列に含まれ、かつ `utcMinute === 0` のときだけ EN バッチとして動く（Cron がその時刻に叩く前提）。
- 現状: `[0, 4, 8, 12, 16, 20]` → 1 日 6 回・**4 時間ごと**。窓は `EN_SEARCH_WINDOW_MINUTES = 240` で、doc（AFFILIATE_RECRUIT_SEARCH_WINDOW_BY_SCHEDULE）のとおり「6 回 × 4h で 24h を隙間なくカバー」と整合している。

**課題感**

1. **「4 時間ごと」「この時刻」の根拠が書かれていない**  
   なぜ 4 時間なのか、なぜ 0,4,8,12,16,20 なのかがコード・ドキュメントにない。運用指示で決まっているなら「運用指示で固定」と明記されていない。

2. **Cron との一致が前提**  
   Vercel Cron がこの時刻に `affiliate-recruit-run` を叩く前提。時刻を変えるなら Cron と config の両方を揃える必要がある。

3. **窓との整合は取れている**  
   窓 240 分と 4 時間間隔は AFFILIATE_RECRUIT_SEARCH_WINDOW_BY_SCHEDULE で紐づいている。間隔だけ変えると窓とずれ、重複や隙間が出る。

**改善案**

| 案 | 内容 |
|----|------|
| **A. 根拠を明記して現状維持** | 「EN は 4 時間ごと（0,4,8,12,16,20 UTC）。窓 240 分と組み合わせて 6 回で 24 時間を隙間なくカバー。時刻は運用指示で固定。変更時は AFFILIATE_RECRUIT_SEARCH_WINDOW_BY_SCHEDULE および Cron と整合させること」と config または doc に追記。値は変えない。 |
| **B. スケジュール維持のまま触らない** | 変更の必要性がなければコードはそのまま。AGENDA の「スケジュール維持なら触らないでも可」のままにする。 |
| **C. 間隔・時刻を変える場合** | 窓（EN_SEARCH_WINDOW_MINUTES）と「1 日何回か」を決めたうえで、EN_RECRUIT_HOURS と Cron を同時に変更する。例: 6 回/日のままなら窓 240 分はそのままでよい。 |

**推奨**: スケジュールを維持するなら **A（根拠を明記して現状維持）**。運用指示で固定されている旨を書いておけば、あとから「なぜこの時刻か」が分かる。  
→ **案 A で完了**。「運用指示で固定」と config・AUDIT に明記。

### #19 SLOTS_BY_UTC_HOUR の 10 — 課題感・改善案

**役割**

- `SLOTS_BY_UTC_HOUR[utcHour]` はその UTC 時刻のスロット配列。現状は `Array(10).fill("ja")` のように同一言語が 10 個並ぶ。
- run は `hourSent` で `getNextRecruitLangForUtcHour(utcHour, hourSent)` を呼び、`hourSent < slotsThisHour.length` のときだけ実行する。
- Cron（affiliate-recruit-regions）は `0 12,13,17,21,22 * * *` で各時刻に 1 回叩く。

**課題感**

1. **数値 10 に根拠がない**  
   なぜ 10 なのかがコード・ドキュメントにない。batchSize 10 との対応（10 送信/ラン × 10 ラン/時 = 100 DM/時の目安）なのか、単なる上限の目安なのかが不明。

2. **現状は実質 1 ラン/時**  
   各時刻で Cron が 1 回なので、hourSent は 0 の 1 回だけ。スロット数を 1 にしても言語は同じなので「何回まで許容するか」以外の挙動は変わらない。

3. **全スロット同一言語**  
   同じ時刻の 10 スロットはすべて同じ言語（例: 12 時はすべて "ja"）。

**改善案**

| 案 | 内容 |
|----|------|
| **A. 根拠を明記して 10 のまま** | 運用指示で固定。送信成功目標10以外はどうでもよい、と config に明記。 |
| **B. 1 に変更** | 1 時間 1 ランなら `Array(1).fill("ja")` で十分。同じ時刻に複数回叩いても 2 回目以降は no_slot になる。シンプルだが「同じ時間に再実行したい」場合は 1 回しか許容されない。 |
| **C. 運用指示で固定** | #18 と同様「運用指示で固定」とだけ書き、10 の根拠は「運用上の上限」として明記する。 |

**推奨**: 現状の運用（1 回/時）を変えないなら **A（根拠を明記して 10 のまま）** でよい。同じ時刻の再実行をほぼ想定しないなら **B（1 に変更）** で挙動を分かりやすくする選択肢もある。  
→ **運用指示で固定**。config・AUDIT に明記し #19 完了。

| HUSTLE（泥臭いゾーン） | 100 | 3000 |

**改善案**

| 案 | 内容 |

### #21 COEFFICIENT_BY_LANG / REGION_COEFFICIENT — 課題感・改善案

**役割**

- **COEFFICIENT_BY_LANG**: 言語別係数（en:1.15, pt:1.15, es:1.1, ar/ja/ko:1.0）。`getCrConfig()` のデフォルト C として crConfig に渡り、`affiliate-recruit-cr-update.js` でも C の初期値として参照。**run の並び順・除外には未使用**（#15 で recency のみ、crConfig は buildEligibleCandidates に渡すが中で参照していない）。
- **REGION_COEFFICIENT**: 国別係数（IN/PH:1.2, BR:1.15, MX:1.1 等）。コメントでは「BRICS＋周辺の優先度」とあるが、**実装では未参照**。`getRegionCoefficientByLang` は COEFFICIENT_BY_LANG を返しており、REGION_COEFFICIENT は export されているだけでどこからも読まれていない（AFFILIATE_RECRUIT_SCREENING_PRINCIPLES に「将来 lang/region 連携時に未使用」と記載）。

**課題感**

1. **数値に根拠がない**  
   1.15, 1.1, 1.0 等の値がなぜその数字なのかがコード・ドキュメントにない。

2. **並び順・送信判定に効いていない**  
   並び順は recency のみ。run は crConfig を取得するが buildEligibleCandidates 内で C/B を使っていない。アフィリエイター獲得という目的に対して因果が薄い。

3. **REGION_COEFFICIENT は完全に未使用**  
   国別の細分化（IN, PH, BR…）は将来用に定義されているが、現状の run は言語単位でしか見ておらず、REGION_COEFFICIENT を読むコードがない。

**改善案**

| 案 | 内容 |
|----|------|
| **A. COEFFICIENT_BY_LANG は残し doc 化** | crConfig / cr-update が C のデフォルトとして参照しているため削除しない。「言語別 C は CR 用デフォルト。並び順・除外には未使用。数値は運用指示で固定。」と scoring または crConfig にコメント追加。 |
| **B. REGION_COEFFICIENT を削除** | どこからも読まれていないため定数と export を削除。将来使うとき再定義する。 |
| **C. 運用指示で固定** | 送信成功目標10以外はどうでもよい方針に合わせ、「係数は運用指示で固定。因果は薄い。」とだけ明記する。 |

**推奨**: **A** で COEFFICIENT_BY_LANG は「CR 用デフォルト・並び順未使用」と明記。**B** で REGION_COEFFICIENT は未使用のため削除してよい（任意）。  
→ **削除で完了**。REGION_COEFFICIENT と getRegionCoefficientByLang を削除。COEFFICIENT_BY_LANG は crConfig/cr-update 用に残し「並び順・除外には未使用」とコメント追加。

### #25 REF_SENT_TTL — 課題感・改善案

**役割**

- DM 送信時に `ref_sent:{author_id}` を KV に保存するときの有効期限（秒）。現在は `86400 * 90`（90 日）。FirstPromoter 登録時の ref と突き合わせて「DM→登録」の紐づけをするため、funnel API がこのキーを読む。TTL が短いと遅れて登録したユーザーが紐づかず、長いとストレージを消費する。

**課題感**

1. **90 日の根拠がない**  
   なぜ 90 日なのかがコード・ドキュメントにない。コメントでは「ストレージ削減のため 90 日。要短縮時はコードで変更可」とあるが、90 を選んだ理由は未記載。

2. **送信・並び順・除外には効いていない**  
   送信対象の選び方には関係しない。紐づけ・ダッシュボード用。送信成功目標10以外はどうでもよい方針とは直接関係しないが、紐づけ精度とストレージのトレードオフになる。

3. **短縮したい場合のみ検討**  
   AGENDA の「短縮したい場合のみ検討」のとおり、現状のままでも問題はない。根拠を書くか env 化するかは運用次第。

**改善案**

| 案 | 内容 |
|----|------|
| **A. 運用指示で固定** | 「REF_SENT_TTL は 90 日。DM 送信から登録までの想定期間をカバーしつつストレージを抑える目安。運用指示で固定。短縮したい場合はコードまたは env で変更。」と run のコメントに追記。値は変えない。 |
| **B. 触らない** | 現状のコメントのまま。短縮したい場合のみ検討。 |
| **C. env 化** | `REF_SENT_TTL_DAYS` 等で上書き可能にし、デフォルト 90 のまま。変更しやすくする。 |

**推奨**: 紐づけとストレージのバランスで 90 日のままにしてよいなら **A（運用指示で固定と明記）** または **B（触らない）**。変更頻度が高くなりそうなら **C（env 化）**。  
→ **案 A で完了**。運用指示で固定と明記。run にコメント追加。
