# なぜ「解像度の高いスキャン＋6言語コピー」なのに成果が出にくいのか

解像度の高い他者投稿スキャン・引用リポストターゲット抽出・刺さるコピーを6言語で投下するロジックは積んである。それでも期待通りの成果（インプレ・エンゲージ・成約）が上がってこない理由を、**構造要因**と**アルゴ・タイミング**の観点で整理する。意図的に引用リポストをバズらせるために足りていないものをはっきりさせる。

---

## 1. ロジックが「効く」前提と、現実のずれ

| 私たちの前提 | 現実になりうること |
|--------------|---------------------|
| 「伸びている投稿」を引用すれば、そのスレに流れる人数に便乗できる | 引用**元**が伸びていても、**引用ツイートは別のオブジェクト**。X のアルゴは「引用ツイート」の初動エンゲージメントでランク付けする。引用元の熱量は「そのスレを見に来る人数」には効くが、**私たちの引用ツイートが TL に載るかは「私たちの投稿の初動」次第**。 |
| 刺さるコピー＋適切なターゲット選定で CTR・成約が伸びる | **インプレが先**。インプレがほぼゼロだと CTR をどう工夫してもクリック・成約はほぼ 0。まず「私たちの引用ツイートが何人に表示されるか」がボトルネック。 |
| 品質スコア・copy fit で「バズる投稿」を選んでいる | 選んでいるのは「**今の検索結果の中では**バズりやすい投稿」。**検索の時間窓（例: 直近30分）が広いと、本当に伸び盛りの 2〜7 分の投稿は母数が少ない**。結果として「10〜30分前に投稿された、すでに伸び止まりつつある投稿」を引用している可能性がある。 |
| 1 run で cap まで投稿すれば volume は足りる | run 間隔（例: 3h）× 1 run あたり 1 言語のみ。**言語ごとの実行頻度**と**「伸びている時間帯」との一致**がずれていると、当たり本数が少ない。また **btcSnapshot が KV にないと run 全体が SKIP** される。Cron の順序・タイミングで多くの run がスキップされている可能性。 |

---

## 2. 引用リポストが「バズる」ために必要なこと（X のアルゴに近い理解）

1. **初動のエンゲージメント**  
   X は投稿直後の数十分で「テスト」し、いいね・リプライ・RT が付かないと TL から外す。**引用ツイート単体**の初動が弱いと、どれだけ良い引用元を選んでも私たちの投稿は伸びない。

2. **「乗るタイミング」**  
   引用元が **今まさに伸びている最中（2〜7 分〜数十分）** のときに、私たちの引用が載るのが理想。検索窓が 30 分だと、取得した時点で投稿はすでに 5〜30 分経過している。**検索〜選定〜投稿までのラグ**を考えると、「2〜7 分の伸び盛り」に乗り切れていない可能性が高い。

3. **アカウントの「権威」**  
   同じ引用・同じコピーでも、フォロワー数・過去のエンゲージメントが大きいアカウントのほうがアルゴに拾われやすい。新規寄り・フォロワー少なめだと、**ロジックが正しくても初動のテストで負けやすい**。

4. **引用ツイートの扱い**  
   X は「引用リポスト」をオリジナルツイートと同じように流すとは限らない。**引用は「会話の枝」として扱われ、配信が抑えられる**可能性がある。それでも「引用元のスレに来た人には表示される」ので、引用元の伸び具合は重要。

---

## 3. 実装・運用まわりで成果を阻害しうる点

| 要因 | 内容 | 確認・打ち手 |
|------|------|----------------|
| **検索窓が広い** | デフォルト 30 分。伸び盛り（2〜7 分）の投稿は母数が少なく、選定結果が「すでにやや古い投稿」に偏りやすい。 | **BUZZWEAVE_SEARCH_WINDOW_MIN** を 10〜15 に短縮して「より直近の投稿」を優先。低 volume 言語では 0 件になるリスクがあるので、フォールバックで窓を広げる実装にする。 |
| **run あたり 1 言語** | 6 言語 round-robin で 1 run に 1 言語だけ。言語ごとの実行回数が少なく、「その言語で盛り上がっている時間帯」とずれやすい。 | 実行回数増（**BUZZWEAVE_MIN_RUN_INTERVAL_HOURS** 短縮）や、時間帯別に言語を振るスケジュールの検討。 |
| **Snapshot スキップ** | btcSnapshot が KV にないと **SKIP_NO_SNAPSHOT** で run 全体が走らない。 | Cron で `/api/cron`（またはスナップショット投入）が **buzzweave-run より先**に確実に実行されているか確認。 |
| **dryRun の扱い** | buzzweave-run の dryRun は **クエリの dry_run のみ**参照。**X_POSTING_DRY_RUN** は参照していない。 | 本番で「投稿しない」意図で X_POSTING_DRY_RUN=true にしている場合、buzzweave-run は **投稿してしまう**。必要なら API 側で X_POSTING_DRY_RUN も見て dryRun を決定する。 |
| **初動をコードでどうにかする** | 初動のいいね・リプライは「誰かが反応する」必要がある。テンプレの質問・オープニングでリプライを誘う程度はできるが、**アルゴのテストに通るかはコンテンツ・アカウント・時間帯の総合力**。 | テンプレの engagement 誘発（質問・「要チェック」など）を強める。時間帯・言語別の our_impressions を分析し、**インプレの出る条件に配分を振る**。 |

---

## 4. 「意図的に引用リポストをバズらせる」ために足りそうなもの

1. **時間解像度を上げる**  
   - 検索窓を短くして「今まさに伸びている」投稿を多く含める。  
   - 選定は **経過時間（age）を強く見る**（例: 2〜10 分を最優先）。  
   - 検索〜投稿までの処理をできるだけ短くし、「伸び盛りに乗る」確率を上げる。

2. **「私たちの引用ツイートの初動」を意識する**  
   - 同じテンプレの連打を避ける（diversity）。  
   - 価値先行・質問でリプライを誘う（既存 PQT 設計の強化）。  
   - リンク・宣伝っぽさを抑え、アルゴの demote を避ける。

3. **実データで「何が効いているか」を切る**  
   - **buzzweave_post_log** の our_impressions を、**言語・クラスタ・UTC 時間帯・引用元の velocity / engagement** で集計。  
   - インプレの出る条件（言語・時間帯・run タイミング）に **投稿本数・run の時刻**を寄せる。

4. **アカウント側**  
   - フォロワー・エンゲージメントはコードでは変えられない。PQT は「他者のリーチに便乗する」戦略のまま、**引用元の質とタイミング**と**自投稿の初動を最大化する**ところまでコードでやる。

---

## 5. まとめ

- **ロジックは「良い引用元を選び、刺さるコピーで 6 言語投下する」までできている。**  
- **成果が出にくい主因は、(1) 引用ツイートの配信・初動がアルゴに依存していること、(2) 検索・選定の時間解像度（窓の広さ・乗るタイミング）、(3) run の実行条件・頻度・言語配分、(4) アカウントの権威、の組み合わせ**と考えられる。  
- **意図的にバズらせる**には、**時間解像度の引き上げ（検索窓短縮・age 優先・処理遅延削減）**と、**インプレの出る条件の分析と配分最適化**をセットで回す必要がある。

次のステップ例: **BUZZWEAVE_SEARCH_WINDOW_MIN=15** で試す、buzzweave-run で **X_POSTING_DRY_RUN** を参照する、**analyze-our-pqt-buzz.js** で言語・時間帯別インプレを出して run の時刻・言語を調整する。
