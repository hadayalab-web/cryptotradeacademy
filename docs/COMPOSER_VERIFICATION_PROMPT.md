# Composer 検証用プロンプト（実験）

Gemini / Grok と同じ基準で Composer（Cursor）を検証する。Composer は編集を試みがちなので、**「ファイルは編集せず、このチャットに回答だけ書け」** と毎回明示する。以下を Composer に貼って実行し、出力を記録する。

---

## 実験1: 「次の1アクションだけ」を守るか（正しいレバーか）

**プロンプト（そのまま Composer に貼る）:**

```
ファイルは編集しないでほしい。このチャットに回答だけ書いてくれ。

あなたは ML-PQT の run 解析担当。以下のログだけを前提に答える。

【直近 run】
- lang: es
- posts_fetched=13, candidates=10, slots=4, cap=63, posted=4, fill_rate≒6.3%
- pagesFetched=1（全クエリ）, lowVolumeBackfillUsed=false

指示: この run の「原因」を1行で書いたあと、「次の1アクション」（変更するパラメータと値）を1つだけ出し、その理由（因果）を1行で書け。共感・謝罪・受け取り確認・チェックリスト・「必ず見る指標」の羅列は一切出すな。3ブロックだけ: 原因 / 次の1アクション / 理由。コードや設定ファイルの変更はしない。
```

**検証ポイント:**
- 原因が「検索ヒット不足→候補枯渇」かどうか
- アクションが「BUZZWEAVE_SEARCH_WINDOW_MIN 拡大」か「fallback 増」か「lowVolumeBackfillUsed=true」か（正解は SEARCH_WINDOW_MIN 拡大のみ）
- 共感・謝罪・チェックリストを追加していないか
- **ファイルを編集しようとしていないか**（編集しようとしたら不合格）

---

## 実験2: A/B で選ばせたとき（レバーの選択）

**プロンプト（そのまま Composer に貼る）:**

```
ファイルは編集しないでほしい。このチャットに回答だけ書いてくれ。

ML-PQT run の結果: posts_fetched=13, slots=4, cap=63, posted=4。fill_rate が低い。

次のどちらを先にやるべきか、理由付きで1つだけ選べ。
A) BUZZWEAVE_SEARCH_WINDOW_MIN を 15→30 に変更する
B) BUZZWEAVE_FALLBACK_SLOT_COUNT を 3→5 に変更する

答えは「A または B」と「理由（1行）」だけ。前置き・共感・その他の説明は不要。コード変更はしない。
```

**検証ポイント:**
- 正解は A
- 余計なブロックや編集の提案をしていないか

---

## 実験3: 「末尾に何も足すな」を守るか

**プロンプト（そのまま Composer に貼る）:**

```
ファイルは編集しないでほしい。このチャットに回答だけ書いてくれ。

実験1と同じ前提（es, posts_fetched=13, slots=4, cap=63, posted=4）。原因・次の1アクション・理由の3ブロックだけ出せ。そのあとに「ご提示いただいた〜」「他に検証したいパターンがあれば」などの受け取り確認や追加依頼の誘いは一切書くな。3ブロックで終えて、それ以降は文字を出力しない。コードや設定の変更はしない。
```

**検証ポイント:** 3ブロックの直後に受け取り確認・追加依頼の誘いが一切ないか。編集を始めていないか。

---

## 結果の記録（実験後に埋める）

| 実験 | 原因を正しく書いたか | アクションは正しいレバーか | 共感・謝罪・チェックリストを出したか | 末尾の受け取り確認・追加依頼の誘い | ファイル編集を試みたか | 備考 |
|------|---------------------|---------------------------|-------------------------------------|-----------------------------------|------------------------|------|
| 1    |                     |                           |                                     |                                   |                        |      |
| 2    | A/B 正解            | -                         |                                     |                                   |                        |      |
| 3    | -                   | -                         | -                                   | 3ブロック以外を出したか            |                        |      |

**判定:** 3つとも「原因・正しいレバー・無駄なし・末尾クリーン・編集しない」なら合格。Gemini 通過済み。Grok は 1・2 で誤レバー。

**Composer 実測結果:** 3実験とも合格。原因・正しいレバー（SEARCH_WINDOW_MIN 拡大）・理由・A 選択・編集なし。3つまとめて投げたため「ファイルの全文を読み、各プロンプトへ回答します」の前置きあり。1本ずつ投げれば前置きは出ない可能性あり。

## 最終試験

Gemini と共通の最終試験は **`docs/COMPOSER_GEMINI_FINAL_EXAM.md`** を参照。複数 run の合成・ワナ（lowVolumeBackfillUsed 誘導）・3ブロック厳守・編集しない。同じプロンプトを Composer に投げて合否を記録する。
