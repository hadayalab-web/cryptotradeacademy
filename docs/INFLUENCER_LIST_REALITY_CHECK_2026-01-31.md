# インフルエンサーリストの現実チェック
## 824/840の根拠と品質 — 正直な整理と次の一歩
**作成日**: 2026-01-31

---

## 1. あなたの疑問は正当です

- 「824という数字に根拠があるのか」
- 「Grokで抽出したリストが、本当に高インプレッション・高エンゲージメントを出せる質なのか」
- 「Cursor/Composer 1を信じすぎて苦しんでいる」

**結論から言うと: 824/840 には戦略的・エビデンス的な根拠はなく、リストの「質」は現状「Grokの言い分」だけで、実データで検証されていません。** 以下で根拠と対策を整理します。

---

## 2. 824 と 840 の正体

### 840 の由来

- ドキュメント上は「前回分析」「Grok深掘り」「SSOT推奨」と書かれているが、**その「前回分析」が何に基づいているかは明示されていない**。
- 実態は **「Grok の過去の分析で 840 人推奨と返した → それをそのまま目標数にした」** という循環。
- 言語配分（EN:210, ES:168, PT-BR:168, AR:112, JA:98, KO:84）も **「深掘り分析に基づく最適配分」とあるだけで、出典・根拠はない**。
- 業界ベンチマークやKPI逆算（例: 128投稿/日で十分）から「840人必要」と導いたわけではない。

→ **840 は「Grokが言った目標数」であり、エビデンスベースの最適人数ではない。**

### 824 の意味

- **「2週目で Grok から実際に取得できた人数が 824 人だった」** という実績値。
- 840 に足りない分は PT-BR と KO の不足（目標未達）。
- 戦略的に「824人だからこうする」と導いた数字ではなく、**単に「今ストックにある人数」**。

→ **824 は「たまたま今ある人数」。逆算戦略で必要な人数から算出した値ではない。**

### 逆算ドキュメントとの関係

- `REVERSE_STRATEGY_824_INFLUENCERS_2026-01-31.md` では「128投稿/日で十分」「824人を均等に回せば 0.16 投稿/人/日で足りる」と書かれている。
- ここで使っているのは **「すでに 824 人在る」という前提** であり、「824 人必要だから 824 人取る」という設計ではない。
- つまり **「人数の根拠」ではなく「今ある人数で運用設計する」** 文書。

---

## 3. リストの「質」は検証されていない

### Grok が返しているもの

- `discoverInfluencersForQuoteRepost`（`services/grok/client.js`）は **X (Twitter) API を叩いていない**。
- **LLM が「こういうアカウントがいるはず」と推測で** `username`, `tweetId`, `engagementRate`, `recentImpressions`, `followerCount` を返している。
- したがって:
  - **tweetId が実在するか** → 未検証
  - **engagementRate / recentImpressions が本当か** → 未検証（Grokの推定のまま）
  - **高インプレ・高エンゲの「質」** → Grokのプロンプト基準を満たすと「言っている」だけ

### 実際のデータの怪しさ

- `data/influencers/influencers-ko.json` 等を見ると、`tweetId` が **1846823456789012345**, **1846712345678901234** のような連番・パターンに見える値になっている。
- 実在するツイートID（スノーフレーク）はもう少しランダムな印象になることが多く、**Grokがでっち上げた・推測したIDの可能性が高い**。
- そのまま引用リポストに使うと **「存在しないツイートを引用している」** となり、投稿失敗や無効な投稿になるリスクがある。

### 現状の検証の範囲

- 実装でやっているのは **tweetId が 18–19 桁の数字か** という形式チェックと、username の有無程度。
- **そのツイートが X 上に実在するか** はチェックしていない。
- 投稿後に **X API や Webhook で実インプレッション・エンゲージメント** は記録しているが、**リスト構築時点での「質」の保証には使っていない**。

→ **「高インプレ・高エンゲになる質の良いリスト」かどうかは、現状では誰も保証していない。疑ってかかるのが正しい。**

## 4. やるべきこと — 品質を「実データ」で取りにいく

### 4.1 方針

- **人数（824/840）より「質」を優先する。**
- **Grok の出力を「そのまま信じる」のではなく、「実データで検証し、良いものだけ残す」運用にする。**

### 4.2 すぐできること（実測で検証）

1. **投稿後の実測を活用する**
   - 引用リポストはすでに `recordEngagementMetrics` / Webhook で **実インプレッション・エンゲージメント** を記録している。
   - KV の `x:webhook:stats:influencer:{username}` 等で、**どのインフルエンサーが実際にインプレ・エンゲを稼いでいるか** を集計する。
   - **実測で上位のインフルエンサーを残し、下位はリストから外す or 補充候補にする** と、「質」に基づいたリストに近づく。

2. **tweetId の実在チェック（サンプルでよい）**
   - X API の「ツイート取得」で、リストから抜いた tweetId が **実在するか** をサンプル確認する。
   - 存在しないIDが多ければ、その言語のリストは **Grok の再取得 or 手動リスト** で見直す必要がある。
   - **スクリプト**: `node scripts/validate-influencer-tweet-ids.js --lang ko` または `--lang en --sample 20` で、`data/influencers/influencers-{lang}.json` の tweetId を X API で検証できる。実在率が低い場合はリスト見直しを推奨。

3. **目標数の再設計（任意）**
   - KPI（例: 128投稿/日）から **「必要なプールサイズ」** を逆算するなら、`REVERSE_STRATEGY_824_INFLUENCERS` の考え方でよい。
   - その場合、**840 は「十分な余裕を持った目標」** として扱い、**「824 いれば足りる」は「今の人数で運用設計できる」という意味** に留める。
   - **まずは「質の高い少人数」で実測を積み、インプレ・エンゲが取れることを確認してから人数を増やす** 方が安全。

### 4.3 運用で守ること

- **インフルエンサーリストの補充・リフレッシュは手動のみ**（Cron で自動取得しない）というポリシーはそのまま。
- 補充するときは:
  - Grok で再度取得する場合でも、**可能なら tweetId の実在チェック or 実測ランキングと組み合わせる**。
  - あなたと Grok で「リストの質」を一緒に点検・リフレッシュする、という運用が現実的。

| 項目 | 現実 |

**次の一歩:**

1. **実測でランキング** — Webhook/engagement の実データで「どのインフルエンサーが稼いでいるか」を可視化し、上位を残して下位を入れ替え候補にする。
2. **tweetId の実在チェック** — サンプルで X API または手動で確認し、存在しないIDが多い言語はリストを見直す。
3. **質優先** — 「824人いれば十分」は「今の人数で運用できる」という意味に留め、**まず質を検証してから人数を信じる**。

Cursor/Composer 1 由来の「824」「840」「Grokが返したリスト＝高品質」は、そのまま信じず、**実データで検証し直す**ことで、苦しい状態から抜け出す一歩にしてください。
