## 1) 週末までに$100,000達成するために必要な技術実装（最短距離の必須セット）

### A. 「配信」＝DM/Emailの本番投入（最優先）
- **送信ジョブキュー化**（同期送信は禁止）
  - 送信対象をキューに積み、ワーカーが順次送る（失敗時の再送が可能）
- **レート制限 + バックオフ**
  - Telegram/Emailともに、スロットリング（例：秒間/分間上限）と指数バックオフ
- **Idempotency（重複送信防止）**
  - `campaign_id + user_id + channel` で一意キーを持ち、二重送信を防ぐ
- **テンプレ変数の検証**
  - 生成したSL/DMが空・NGワード・URL欠落などの場合は送信前に弾く

### B. 「計測」＝リアルタイムKPIの可視化（配信と同じくらい重要）
- 最低限必要なイベント：
  - `lead_loaded` / `message_queued` / `message_sent` / `message_failed`
  - `link_clicked`（短縮URL/リダイレクトで計測）
  - `reply_received`（Telegramなら受信Webhook/ポーリングで取得）
  - `call_booked` / `payment_started` / `payment_succeeded`（決済/予約ツール連携）
- **ダッシュボード**（最短はGoogle Sheets/Looker StudioでもOK）
  - 市場別・チャネル別・キャンペーン別のファネル（送信→到達→クリック→返信→成約）

### C. 「運用」＝アラートと自動レポート（止血の速度が売上を決める）
- しきい値アラート（例）
  - 送信失敗率 > 5%（5分移動平均）
  - クリック率が市場平均から急落
  - キュー滞留（未処理件数が増加）
- **定時レポート**（1時間ごと/3時間ごと）
  - COO/CEOへ：市場別の送信数、返信数、予約数、売上、直近のボトルネック

### D. 「信頼性」＝再送・履歴・監査ログ
- リトライポリシー（例：最大5回、指数バックオフ、致命エラーは即停止）
- 送信履歴（誰に、いつ、何を、結果、エラー内容、再送回数）

## 2) DM送信機能を24時間以内に実装する具体計画（実装手順）

### 方針（24hで「動く・測れる・止められる」まで持っていく）
- **Telegramは Bot API だけで完結しない**点に注意  
  - 一般ユーザーへのDMは「相手が先にBotを開始」している必要があるのが原則。  
  - もし「ユーザーがすでにBotに接触済み」のリストならBot送信でOK。  
  - 未接触ユーザーへ“いきなりDM”を想定しているなら、技術というより**規約・到達性の壁**があるので、即日で確実なのはEmail優先＋Telegramは「接触済み/返信済み」セグメントに限定が安全。

### 0) 事前確認（1時間以内）
- リードの属性確認：
  - Telegram: `chat_id` を保持しているか？（保持していないなら即DMは不可）
  - Email: アドレスの有無、バウンス想定
- 送信対象市場（6市場）の言語テンプレとリンク先（VSL/LP/決済）の準備状況

### タイムライン（24h）

#### T+0〜3h：設計・土台
- データモデル（最低限）
  - `leads(id, market, tg_chat_id?, email?, name, status...)`
  - `messages(id, campaign_id, lead_id, channel, payload, status, error, sent_at, retry_count)`
  - `events(id, type, campaign_id, lead_id, meta, ts)`
- 送信状態遷移
  - `queued -> sending -> sent | failed | skipped`
- レート制限の方針決定（市場/チャネル別）

#### T+3〜10h：Telegram送信（可能な範囲で）＋受信計測

  - `sendMessage(chat_id, text, parse_mode, disable_web_page_preview)`
- エラーハンドリング
  - 403（ブロック/未開始）→ `skipped` へ
  - 429（rate limit）→ `retry` with backoff
- 返信取得
  - Webhook設定（可能なら） or ポーリング
  - `reply_received` をイベント化

#### T+10〜16h：Email送信（確実にスケールさせる）
- 送信プロバイダ（最短で安定するもの）
  - SendGrid / AWS SES / Mailgun のいずれか（既存契約優先）
- バウンス/スパム対策（最低限）
  - 送信ドメインのSPF/DKIM（既にあれば流用）
  - 失敗は `failed` にして再送はエラー種別で分岐（恒久失敗は打ち切り）
- クリック計測
  - 短縮URL（自前リダイレクト）で `link_clicked` 取得

#### T+16〜20h：KPIダッシュボード・アラート
- 集計（campaign/market/channel別）
  - sent数、failed率、CTR、reply率、booking率、CVR、売上
- アラート
  - Slack/Telegram（CEO通知機能を流用）へ「失敗率」「キュー滞留」「CTR急落」を送信

#### T+20〜24h：負荷試験・本番投入・運用手順
