# X API 公式仕様確認用 — Grok へのプロンプト

以下を Grok（または X API 公式リファレンス）に投げ、返答をこのファイルの「回答メモ」に追記して運用に活用する。

## プロンプト（コピペ用）

```
X API (Twitter API v2) の公式仕様について、以下の3点を教えてください。開発している Bot のパラメータ設計と障害対応のため、公式ドキュメント・ベストプラクティスに基づいた回答をお願いします。

1. **Rate limit（レート制限）**
   - **GET /2/tweets/search/recent** と **POST /2/tweets** について、アプリ／ユーザーあたりの制限（リクエスト数/時間単位など）を教えてください。
   - 1回の run で search/recent を「クエリ2本 × 1クエリあたり3ページ」で叩き、その後 POST /tweets で最大20件程度投稿する運用を想定しています。1日に such run を複数回（例: 9回）行う場合、レート制限に引っかからない目安や注意点はありますか。

2. **検索の時間範囲（start_time / end_time）**
   - search/recent で「直近15分」や「直近30分」のツイートを取得するとき、**start_time** と **end_time** の指定方法で、公式が推奨している書き方や制約（例: 最大何分前まで有効、UTC 指定の要否など）はありますか。
   - 検索の鮮度とヒット数を両立させるうえで、時間範囲のベストプラクティスがあれば教えてください。

3. **402 Payment Required**
   - 402 が返る主な条件（例: クレジット枯渇、プラン上限など）を教えてください。
   - 402 発生後、解消までの目安時間や、再試行の推奨（例: 一定時間あけてから再送する等）はありますか。開発側で「402 が出たら一定時間はリクエストを控える」といった運用をしたい場合の目安を知りたいです。

引用元（公式ドキュメントの URL や該当セクション）があれば、あわせて教えてください。
```

## 回答メモ（Grok の返答）

### 1. Rate limit（レート制限）

Twitter API v2 のレート制限は、認証方式（User 認証 vs App 認証）とアクセスレベル（Essential/Free, Basic, Enterprise）により異なる。主に **15分間スライディングウィンドウ** でカウントされ、レスポンスヘッダー（`x-rate-limit-limit`, `x-rate-limit-remaining`, `x-rate-limit-reset`）で確認可能。

- **GET /2/tweets/search/recent**
  - User 認証（OAuth 1.0a User / OAuth 2.0 User）: **180 リクエスト / 15分**（ユーザーあたり）
  - App 認証（OAuth 2.0 App）: **450 リクエスト / 15分**（アプリあたり）
  - Free プラン（Essential）では読み取り制限あり。**Basic プラン以上で安定運用推奨**
- **POST /2/tweets**
  - User 認証: **200 リクエスト / 15分**（ユーザーあたり）。※App 認証不可（ユーザーコンテキスト必須）
  - 1 リクエスト = 1 ツイート。20 件投稿 = 20 リクエスト

**運用例の目安**（1 run: search 2 クエリ×3 ページ = 6 リクエスト + POST 20 件 = 20 リクエスト、1 日 9 回）:
- 合計 26 リクエスト/run。User 認証なら search 180/15min・POST 200/15min で余裕あり
- 1 日 9 回（234 リクエスト/日）でも、15 分ウィンドウ内で集中させなければ問題なし
- **引っかからない目安**: run 間隔を **30 分以上** 空ける（15 分ウィンドウクリア）。9 回を 2〜3 時間おきに分散
- 超過時は **429 Too Many Requests**。`Retry-After` ヘッダー遵守。`remaining < 50` で待機/バックオフ推奨

**引用元**: Rate limits overview, Search Tweets (recent) – Rate limit, Manage Tweets (POST) – Rate limit, Access levels & pricing

---

### 2. 検索の時間範囲（start_time / end_time）

GET /2/tweets/search/recent は **過去 7 日間** が対象（リアルタイムではない）。`start_time` / `end_time` は **UTC の ISO 8601（YYYY-MM-DDTHH:mm:ssZ）必須**。

- **start_time**: 最古の取得時刻。最大 7 日前まで（超えると無効）
- **end_time**: 最新の取得時刻。現在時刻を超えると無効
- **時間範囲**: 1〜168 時間（7 日）。狭すぎるとヒット 0、広すぎるとノイズ・レート消費増
- **直近 15 分の例**: `end_time = UTC now`, `start_time = now - 15min`
- **ベストプラクティス**: 鮮度優先なら 5〜30 分範囲。ヒット数両立なら初回 1〜2 時間で傾向把握後、狭く調整。`max_results=100` 併用
- **注意**: 検索インデックスに数分遅延あり。完全リアルタイムは不可

**引用元**: GET /2/tweets/search/recent – Parameters, Search concepts – Time recency

---

### 3. 402 Payment Required

**主な条件**:
- 月間ツイート投稿キャップ超過（Basic: 50,000 件/月, Pro: 1,000,000 件/月）
- プリペイドクレジット枯渇 / 支払い未完了
- プラン変更直後の一時的（稀）
- 読み取りで Basic 未加入時（Free は投稿のみ）

**解消目安と再試行**:
- **解消時間**: **月次リセット**（カレンダー月初 UTC 00:00）。超過後は即リセットなし（月末まで待機）
- **運用目安**: 402 検知後、残月日数分控える。またはプランアップグレード（数分で反映）
- **開発側**: 402 時はログ記録後 **24〜48 時間バックオフ**。月初にキャップ確認。ダッシュボードで残キャップ監視。投稿量予測（日次 = 月上限/30）で回避

**引用元**: Error troubleshooting, Error codes & responses – 402, Pricing & monthly caps, Platform use rules

## 現在の料金（X API ダッシュボード・従量課金）

※ Grok の「Basic 50,000 件/月」は古い情報。現状は**リソース/リクエストごとの従量課金**。クレジット上限（例: $8）を設定していれば請求はその範囲で頭打ち。

| カテゴリ | 単価 | 備考 |
|----------|------|------|
| **投稿: 読み取り** | $0.005 / リソース | search/recent で取得したツイート数など |
| **ユーザー: 読み取り** | $0.010 / リソース | ユーザー情報の取得 |
| **コンテンツ: 作成** | $0.010 / リクエスト | 投稿（PQT）1 本 = 1 リクエスト |
| DM イベント: 読み取り | $0.010 / リソース | - |
| DM インタラクション: 作成 | $0.015 / リクエスト | - |
| ユーザーインタラクション: 作成 | $0.015 / リクエスト | - |

**BuzzWeave の目安**: 1 run あたり 検索で数十リソース読み取り + 投稿 最大30 リクエスト（作成）。9 run/日なら 作成だけで 270 リクエスト/日 ≈ $2.70/日（作成のみ）。読み取り分を足すと月額で数十ドル規模になりうるが、**クレジット上限（$8 等）を設定していればその範囲で止まる**。

## 1日あたりの X API コスト計算（BuzzWeave）

**前提**: 8 run/日、1 run あたり 検索 2 クエリ×3 ページ（maxResults=50）、レスポンスに `data`（ツイート）と `includes.users`（投稿者）が含まれるとする。

| 項目 | 単価 | 1 run あたり | 8 run/日 |
|------|------|--------------|----------|
| **投稿: 読み取り** | $0.005/リソース | 2×3×50 = 300 件（最大） | 2,400 件 → **$12.00** |
| **ユーザー: 読み取り** | $0.010/リソース | 同上で最大 300 ユーザー | 2,400 件 → **$24.00** |
| **コンテンツ: 作成** | $0.010/リクエスト | cap 100（実際はスロット次第） | 最大 800 件 → **$8.00** |

**合計（最大フル回転時）**: 約 **$44/日**（読み取り $36 + 作成 $8）。※ 実データでは read/create 比はもっと低いことが多い（下記「実データによる検証」参照）。

**典型例**（検索で 1 ページあたり 30 件・2 ページ止まり、投稿 40 本/run）:
- 読み取り: 2 クエリ×2 ページ×30 = 120 投稿 + 80 ユーザー → (120×0.005 + 80×0.010)×8 run ≈ **$11.20/日**
- 作成: 40×8 = 320 → **$3.20/日**
- **合計 約 $14.40/日**

**控えめ**（検索 1 ページ 20 件、投稿 20 本/run）:
- 読み取り: 2×1×20 = 40 投稿 + 25 ユーザー → (40×0.005 + 25×0.010)×8 ≈ **$3.60/日**
- 作成: 20×8 = 160 → **$1.60/日**
- **合計 約 $5.20/日**

クレジット上限を **$8** にしている場合、最大〜典型では 1 日で達する。上限で請求が止まるため、実支払いは $8 以内に収まる。

## JST 19時以降 24時間の想定（1日分と同様）

**対象**: JST 19:00 〜 翌日 JST 19:00（= UTC 10:00 〜 翌 UTC 10:00）。Cron は UTC 0,3,6,9,12,15,18,21 のため、この 24h に **8 run すべて** が含まれる（＝実質 1 日分）。

| 項目 | 想定 |
|------|------|
| **想定投稿数** | **200〜400 本**（典型 250）。日次ターゲット・trapScore・Fisherman 数・dailyLimit で変動。1 run あたり cap 25〜50 程度。 |
| **X API 費用** | **典型 約 $14.40**（読み取り $11.20 + 作成 $3.20）。控えめで **約 $5.20**、最大フルで **約 $44**。クレジット上限 $8 の場合は **実支払い $8 以内**。 |
| **獲得インプレッション数** | **約 5万〜20万**（保守的 5万〜12万、伸びれば 15万〜25万）。30–50 PQT/日で 7–8万の運用目安をベースに、200–400 PQT/日では希釈を考慮してスケールするとこのレンジ。Grok の「高ボリューム時 50k–250k」の中央付近。 |

※ インプレッションはアルゴ・成約品質・時間帯に依存するため、あくまで見積もり。実測は X Analytics や funnel で確認すること。

## 実データによる検証（実証実験）

**実測サマリ**（ある期間の X API ダッシュボード）:
- **総費用**: $104.00
- **総投稿数（Read）**: 13.89K 件 → 投稿: 読み取り
- **Total Users**: 563 件 → ユーザー: 読み取り
- **総リクエスト数**: 14.81K（Create + Read などの合計）
- 日別の「Content Create」合計 ≈ 2,893 リクエスト（投稿作成）

**逆算**:
- 投稿: 読み取り 13,890 × $0.005 = **$69.45**
- ユーザー: 読み取り 563 × $0.010 = **$5.63**
- コンテンツ: 作成 2,893 × $0.010 = **$28.93**  
→ **合計 $104.01** ✓

**トリッキーな点（実モデルの整理）**:
1. **ダッシュボードの「Read」= 投稿: 読み取りのみ**。ユーザー読み取りは別カウント（Total Users）。
2. **Read が日によって大きくぶれる**: 例として Feb 12 に Read 3,836、Feb 1 に 2,293。検索でヒットが多い日は読み取りコストが跳ねる。
3. **Create との比**: 実データでは 13,890 read / 2,893 create ≈ **約 4.8 投稿読み取り/1 作成**。理論上の「最大 300 read/run」よりかなり少ない平均になっており、検索結果数・ページ数・run 数で実際の read は変動する。
4. **コストの大部分は読み取り**: この期間で $75（Read） vs $29（Create）。投稿数を増やしても、検索の取り方次第で読み取りが効き、**単純に「作成だけ」で見積もると甘くなる**。

見積もりするときは「読み取りが日次でスパイクしうる」「Read = 投稿リソース、User は別」を前提にした方が安全。
