# 🚀 インフルエンサー発見プロセス最適化案（強化・拡張版）

## 1. 階層バランスの改善（強化版）

現状の「100% Top階層」問題は、LLMが「インフルエンサー」という言葉から「有名人」を連想するバイアスによるものです。これを解決するには、**階層ごとの「ペルソナ定義」と「クォータ制（割当制）」の導入**が必要です。

### 1.1 プロンプトエンジニアリング戦略：ペルソナ別プロンプト

単に数値範囲を指定するだけでなく、Grokに対して「誰を探しているか」のコンテキストを与えます。

**プロンプトテンプレート（概念図）:**
```json
{
  "role": "system",
  "content": "あなたは暗号資産市場の専門リサーチャーです。現在、{{TARGET_TIER}}層のインフルエンサーを発掘するタスクを負っています。"
},
{
  "role": "user",
  "content": "以下の条件に合致するX (Twitter) ユーザーを{{BATCH_SIZE}}人抽出してください。\n\n[ターゲット層: {{TARGET_TIER_NAME}}]\n- 定義: {{FOLLOWER_RANGE}}のフォロワーを持つアカウント\n- 特徴: {{TIER_CHARACTERISTICS}}\n- 除外: 既に有名なアカウント、ニュースBot\n\n[検索キーワード]\n{{KEYWORDS}}\n\n[出力形式]\nJSON形式 (username, estimated_follower_tierのみ)"
}
```

**階層ごとの検索クエリ定義:**

| 階層 | 変数名 | フォロワー範囲 | 特徴 (Characteristics) | 検索の狙い |
|------|--------|----------------|------------------------|------------|
| **Top** | Macro | 100k - 500k | "業界のオピニオンリーダー、広範なリーチ" | 信頼性、認知度 |
| **Mid** | Mid-Tier | 10k - 99k | "特定のニッチ（DeFi, NFT等）に強い、高いエンゲージメント率" | 実利的な影響力、コミュニティ |
| **Bottom** | Micro | 1k - 9.9k | "新興の分析家、熱狂的なコアファンを持つ、草の根活動家" | 高いCVR、初期トレンド |

### 1.2 段階的取得の実装詳細：クォータ制バッチ処理

1つのリクエストですべてを混ぜるのではなく、APIコール自体を階層ごとに分離します。

**実装ロジック:**
1.  **目標配分の設定**: Top(20%), Mid(50%), Bottom(30%) と定義。
2.  **専用ループの実行**:
    *   `fetchBatch('Top')` を目標数に達するまで実行
    *   `fetchBatch('Mid')` を目標数に達するまで実行
    *   `fetchBatch('Bottom')` を目標数に達するまで実行

**期待される効果**:
*   自然発生的なバイアスを排除し、強制的にMid/Bottom層を収集可能。
*   Mid/Bottom層のクエリでは「hidden gems (隠れた宝石)」「undervalued (過小評価)」といったキーワードを追加することで精度向上。

### 1.3 後処理での階層調整

**アルゴリズム**:
APIから取得したデータに対し、検証フェーズで実際のフォロワー数を取得した後、動的にバケット（分類箱）へ振り分けます。

*   **Overflow Handling**: Top層が目標数を超えた場合、その後のリクエストではTop層を除外するプロンプト（`exclude_follower_count_gt: 100000`）を強化する。
*   **Tier Shift**: 取得時はMid想定だったが実際はTopだった場合、Topの枠を埋めたとみなし、Midの不足分を追加取得するキューを発行する。

## 2. リトライロジックの強化（強化版）

KO/JAの失敗は、単なるタイムアウトではなく「適切な回答が見つからない（または生成できない）」ことに起因します。単純なリトライではなく、**「条件緩和リトライ（Backoff & Relax）」**を導入します。

### 2.1 適応的リトライ戦略（Smart Retry）

リトライごとに戦略を変更します。

*   **Attempt 1 (Normal)**: 詳細な条件、厳密なキーワード。
*   **Attempt 2 (Wait & Retry)**: 5秒待機。同じ条件。
*   **Attempt 3 (Query Rotation)**: キーワードを変更（例: "仮想通貨" → "ビットコイン"、"暗号資産"）。
*   **Attempt 4 (Relax Constraints)**: 制約条件を緩和（例: 「最近のアクティブユーザー」条件を外す）。
*   **Attempt 5 (Cross-Lingual)**: 英語のプロンプトで現地語の結果を求める（Grokは英語指示の方が性能が良い場合がある）。

**言語別パラメータ:**
*   **KO/JA**: 最大8回。Attempt 3以降は「英語プロンプト + 現地語キーワード」モードに切り替え。
*   **EN/ES**: 最大3回（現状維持）。

### 2.2 エラー分類と対応

APIレスポンスを解析し、エラータイプに応じた挙動を実装します。

| エラータイプ | 判定基準 | 対応アクション |
|--------------|----------|----------------|
| **Empty Response** | JSONが空配列 `[]` | クエリのキーワードを変更、または検索期間を広げる。 |
| **Hallucination** | 存在しないユーザー形式 | Temperature（創造性パラメータ）を下げる (0.7 → 0.3)。 |
| **Format Error** | JSONパース失敗 | System PromptでJSON形式を再強調してリトライ。 |
| **Rate Limit** | 429 Error | 指数バックオフ (2s, 4s, 8s...) を適用。 |

## 3. 重複防止の強化（強化版）

トークン制限があるため、全リストをプロンプトに含めるのは不可能です。**「ローリングウィンドウ方式」と「オーバーサンプリング」**を採用します。

### 3.1 取得済みリストの活用（ローリングウィンドウ）

過去に取得した全ユーザーではなく、**「直近のN人（例: 50人）」のみを除外リストとしてプロンプトに渡します**。

**プロンプトへの組み込み:**
```text
[除外リスト]
以下のユーザーは既に取得済みのため、絶対に出力しないでください:
@user1, @user2, ... (直近50件)
```

**期待される効果**:
*   トークン消費を抑えつつ、直近の重複（最も起きやすい重複）を防ぐ。
*   AR/PT-BRでの重複率を90%から10-20%へ低減。

### 3.2 多様性の強制とオーバーサンプリング

**戦略**:
1.  **バッチサイズの拡大 (Oversampling)**: 15人欲しい場合、Grokには「30人」要求する。
2.  **クライアントサイド・フィルタリング**: 返ってきた30人の中から、DB上の全取得済みリストと照合し、重複を除外して先頭15人を採用。
3.  **多様性指標**: プロンプトに「異なるコミュニティ（トレーダー、開発者、ニュース、NFT）からバランスよく選出せよ」と指示。

## 4. Grok APIの応答不良対策（強化版）

KO/JAにおいてGrokが失敗するのは、学習データ内の日本語/韓国語の「クリプト文脈」が英語に比べて希薄だからです。

### 4.1 プロンプト最適化：クロスリンガル・プロンプト (Cross-Lingual Prompting)

**戦略**:
指示（Instruction）はGrokが最も理解しやすい**英語**で行い、検索対象（Target）のみを現地語で指定します。

**JA向けプロンプト例:**
```json
{
  "role": "system",
  "content": "You are an expert at finding Japanese crypto influencers on X."
},
{
  "role": "user",
  "content": "Find 15 Japanese influencers who tweet about 'Bitcoin' or 'Altcoins'.\n\nConditions:\n- Language: Japanese (Must tweet in Japanese)\n- Keywords to look for: 'ビットコイン', '仮想通貨', 'BTC', 'Web3'\n- Exclude: Official exchange accounts.\n\nOutput JSON only."
}
```
※ 以前は日本語で指示していた場合、これを英語指示に切り替えるだけで論理的推論能力が向上することがあります。

### 4.2 代替検索戦略：ハッシュタグ駆動

一般的なキーワードではなく、その言語特有の**Twitterハッシュタグ**を指定します。

*   **KO**: `#비트코인` (Bitcoin), `#이더리움` (Ethereum), `#코인스타그램` (Coinstagram - インスタ用語だがXでも使われる場合あり), `#업비트` (Upbit - 取引所名)
*   **JA**: `#BTC`, `#仮想通貨`, `#Giveaway` (ボットが多いが除外フィルタと併用), `#投資初心者`
*   **期待される効果**: 自然言語処理よりもハッシュタグ検索の方がGrokにとって容易であり、KO/JAのヒット率が劇的に向上する（35% → 70%超）。

## 5. Username長さ制限の解決（強化版）

16文字以上の除外は、Xの仕様とスクレイピング結果の不一致から生じています。

### 5.1 X API制限の確認と正規化

*   **事実確認**: X (Twitter) の `screen_name` (ID) は **最大15文字** です。しかし `name` (表示名) は **最大50文字** です。
*   **原因**: Grokが `screen_name` (@user) ではなく `name` (User Name) を返している、あるいはURLを含んでいる可能性があります。
*   **対応**:
    1.  取得した文字列から `@` マークや `https://twitter.com/` を削除。
    2.  正規表現 `^[A-Za-z0-9_]{1,15}$` で厳密にチェック。
    3.  15文字を超える場合は、それが「表示名」である可能性が高いため、Grokに再問い合わせするか（コスト増）、エラーとして破棄する。

### 5.2 プロンプトでの明示的指示

Grokに対し、表示名ではなくハンドル名（ID）を返すよう強く制約します。

**プロンプト追加:**
```text
IMPORTANT: Return the 'screen_name' (handle without @), NOT the 'display name'.
Constraint: The username MUST be 15 characters or less.
Example: Use 'elonmusk' (valid), DO NOT use 'Elon Musk' (invalid).
```

**期待される効果**:
*   JAで見られた「satoshinakamotojp (17文字)」のような幻覚や、表示名の誤取得を防止。
*   除外率を4-5%からほぼ0%へ。
