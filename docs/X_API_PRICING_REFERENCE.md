## リクルートDMでの使われ方（整理）

- **投稿: 読み取り**: 検索で返ったツイート 1 件 = 1 リソース = **$0.005**（上表のとおり）。
- **ユーザー: 読み取り**: 検索の expansions で返ったユーザー 1 件 = 1 リソース = **$0.010**（上表のとおり）。
- **DMインタラクション: 作成**: 送信成功 1 通 = 1 リクエスト = **$0.015**。403 は課金なし。

→ 課金はすべて **上表の単価・単位** に従う。Read を抑えるには「検索ラン数」より **1 回あたりの取得件数（maxResults・ページ数）** を絞る。詳しくは `X_API_READ_ANALYSIS.md`。

## 実測メモ（Read コスト）

- **観察**: 100 投稿×1 ページ（1 Read）と、30 投稿×5 ページ（5 Read・計 150 投稿）で **Read コストが変わらなかった**（同一期間のダッシュボード比較）。
- **解釈**: 公式は「取得リソース数ごと課金」だが、実請求やダッシュボード表示が **リクエスト数** や別の集計単位になっている可能性がある。あるいは同じ日・同じ枠にまとまって差が出なかった可能性も。
- **運用**: 現時点では「100×1 で十分なら 1 ページに寄せる」は Read 効率（DM/Read）の観点で有効。課金がリソース数で効いていないなら、maxResults を増やしても Read コストは跳ね上がらないかもしれない（要ダッシュボード確認）。

### 今回の $1.09 消費の説明

**手順**: Feb 27 ダッシュボード（DM 14 / Read 7）から**前回控え（DM 8 / Read 5）を引き、今回の試行分だけを抜き出す** → **DM 6 / Read 2**。クレジット $6.5→$5.41 の **$1.09 はこの試行分に対する消費**として分析する。

#### 単価表との一致

| 項目 | 計算 | 金額 | 単価表 |
|------|------|------|--------|
| DMインタラクション: 作成 | 6 リクエスト × **$0.015**/リクエスト | **$0.09** | 上表「$0.015 リクエストごと」と**一致** |
| Read（投稿＋ユーザー） | 下記のとおり | **$1.00** | 上表「投稿 $0.005/リソース」「ユーザー $0.010/リソース」の組み合わせで説明可能（**単価表と矛盾しない**） |
| **合計** | | **$1.09** | |

→ **$1.09 の内訳は単価表と合っている**（DM は一致、Read は表の単価で $1.00 を構成する組み合わせが存在する）。

#### Read $1.00 の内訳 — 計算にもとづく仮説

単価表: **投稿 $0.005/リソース**、**ユーザー $0.010/リソース**。  
Read コスト = (投稿リソース数 × $0.005) + (ユーザーリソース数 × $0.010) = **$1.00**。

**分かっていること**

- 今回増分の **2 Read** のうち **1 Read** は JST 13 ラン（UTC 04:00）で実行。ログ上 **1 ページ・100 投稿** 取得（`fetchOneSearchPage` で maxResults: 100）。検索の expansions で **著者ユーザーも返る**ため、おおよそ **100 ユーザー**（重複除く前）とみなせる。
- もう **1 Read** は、同日他ラン（UTC 0 時ラン以降の別枠や、同一日の別検索）と想定。ログは未確認のため件数は仮定。

**仮説の立て方**

- 2 Read で「生」の取得が 100+α 投稿・100+β ユーザーだったとしても、**Deduplication（同一 UTC 日の同一リソースは再課金されない）** で、**課金されるのはユニークなリソースだけ**。
- 前回控え時点で既に **5 Read（150 投稿＋同数ユーザー程度）** を取得済み。今回の 2 Read は、その一部と重複する可能性が高い。
- 単価表どおりで **$1.00 になる**のは、例: **投稿 100 リソース + ユーザー 50 リソース** → $0.50 + $0.50 = **$1.00**。

**結論（仮説）**

| 内訳 | 課金リソース数（仮） | 単価 | 金額 |
|------|----------------------|------|------|
| 投稿: 読み取り | **100** | $0.005 | $0.50 |
| ユーザー: 読み取り | **50** | $0.010 | $0.50 |
| **Read 合計** | | | **$1.00** |

- **意味づけ**: JST 13 ランで 1 Read あたり 100 投稿＋約 100 ユーザー取得。2 回目の Read は同日の他ランで、**重複控除**の結果、投稿はほぼ重複（新規 0〜少）、ユーザーは **約 50 が新規** とすると、合計 100 投稿＋50 ユーザーで $1.00 と整合する。  
  あるいは、**2 Read 合計でユニークが 投稿 100・ユーザー 50**（2 回とも小さいか、2 回目がほぼ重複）という形でも同じ計算になる。
- いずれにせよ **「Read $1.00 = 投稿 100 リソース + ユーザー 50 リソース」** を、**単価表に合わせたうえでの作業仮説**とする。ダッシュボードに明細は出ないため、検証は別の日の件数・金額の推移で行う。

#### 1 DM あたり $0.18 → コスト圧縮できるか

**現状の 1 DM あたり内訳（今回増分 6 DM / $1.09 ベース）**

| 要因 | 金額/DM | 備考 |
|------|---------|------|
| DMインタラクション: 作成 | **$0.015** | 単価表固定。**圧縮不可**。 |
| Read の按分 | **約 $0.167** | $1.00 ÷ 6 DM。仮説 100 投稿＋50 ユーザーを 6 で割ったイメージ。 |
| **合計** | **約 $0.18** | |

目標 $0.10/DM にするには、Read 按分を **$0.085/DM 以下**にする必要がある（$0.015 + $0.085 = $0.10）。

**圧縮の方向性（できること）**

1. **送信成功数を増やす（10 必達）**  
   同じ Read コストで **10 DM** 送れれば、Read 按分 = $1.00 ÷ 10 = **$0.10/DM**。DM 分 $0.015 と合わせて **$0.115/DM**。目標 $0.10 には届かないが、$0.18 からは明確に下がる。12 DM なら $1.00÷12 ≈ $0.083、**約 $0.098/DM** で目標付近。
2. **Read リソースを減らす**  
   1 ランあたりの取得を減らす（例: maxResults 50、または 1 ページのみに統一）。仮に Read が **$0.50**（投稿 50＋ユーザー 25 相当）で 6 DM なら、$0.09＋$0.50 = $0.59、**約 $0.098/DM**。ただし候補が減り **10 必達が難しくなる**リスクあり。
3. **Deduplication を活かす**  
   同一 UTC 日に同じクエリ・同じ窓で読むと重複控除され、課金リソースが増えにくい。無駄な「読み直し」をやめ、**1 ラン 1 Read で済む設計**に寄せるのは有効。
4. **fields / expansions の見直し**  
   検索で取得するフィールドを必要最小限にすれば、ユーザーリソース数を減らせる可能性はあるが、DM 送信には著者 id が必要なため **削れる幅は小さい**。可能なら API 仕様を確認して検討。

**結論**

- **コスト圧縮は可能。** 効く順は **(1) 10 必達で Read を多くの DM で割る**、(2) 1 ランあたり Read を増やしすぎない（無駄なページを読まない）、(3) 重複控除が効く運用。
- DM 単価 $0.015 は変えられないので、**$0.10/DM に近づけるには「Read をいかに少なく／いかに多くの DM で割るか」** がすべて。現状 $0.18 の大半は Read 按分なので、ここを削るか、送信成功数を増やすかでしか下がらない。

## 公式 Pricing ドキュメントの要点（docs.x.com より）

公式の Pricing 説明から、参照用に要点のみ控える。詳細は [View pricing & purchase credits](https://developer.x.com/#pricing) および Developer Console で確認。

### 仕組み

- **Pay-per-usage**: 従量課金。サブスクなし。使った分だけ支払い。
- **Credit-based**: Developer Console でクレジットを事前購入。API リクエストごとに控除。
- **Per-endpoint pricing**: エンドポイントごとに単価が異なる。**現在の単価は Developer Console で確認**。
- **No commitments**: 契約・サブスク・最低利用料なし。いつでも開始・停止可。
- **Real-time tracking**: Developer Console で利用量・コストをリアルタイム確認。

※ Legacy (Basic/Pro) サブスクの場合は、Developer Console から Pay-per-use へオプトイン可能。いつでも戻せる。

### Deduplication（重要）

**同一リソースは 24 時間（UTC 日）の窓で重複控除される。**

- 同じリソース（例: 同じ Post）を 1 日以内に再度取得しても **追加課金されない**（1 回分のみ）。
- 窓は **UTC 0 時でリセット**。
- 投稿・ユーザーなど **課金対象リソースすべて** に適用。
- 注: Deduplication は **soft guarantee**。大半は重複控除されるが、障害時など一部エッジケースでは控除されない場合あり。

→ 同じツイートを複数回読んでも、同日なら 1 回分の課金で済む可能性がある。実測で「100×1 と 30×5 で Read コストが変わらなかった」と整合する可能性。

### クレジット残高・Auto-recharge・Spending limits

- **残高**: Developer Console に表示。リクエストごとにリアルタイムで控除。
- **注意**: 残高が 0 になるとサービス停止。**ゼロになる前にチャージ**すること。わずかにマイナスになる場合もあり、その間は API がブロックされる。
- **Auto-recharge**: 有効にすると残高がしきい値以下になったら自動でチャージ。Console で設定。
  - **Recharge amount**: トリガー時に追加する金額（例: $25）。
  - **Trigger threshold**: この残高を下回ったら発動（例: $5）。
- **Spending limits**: 請求サイクルごとの最大支出を設定可能。達すると次のサイクルまで API がブロックされる。開発・テスト時の暴れ防止に有用。

### Free xAI API Credits

X API クレジットを購入すると、請求サイクル中の累計支出に応じて **xAI API の無料クレジット** が付与される（最大 20%）。xAI チームを X developer アカウントにリンクする必要あり。

| 累計支出 | 付与率 |
|----------|--------|
| $0 – $199 | 0% |
| $200 – $499 | 10% |
| $500 – $999 | 15% |
| $1,000+ | 20% |

### Monitoring usage（Usage API）

利用量をプログラムで取得するには [Usage endpoint](https://docs.x.com/x-api/usage/introduction) を使用する。

```bash
curl "https://api.x.com/2/usage/tweets" -H "Authorization: Bearer $BEARER_TOKEN"
```

日次の Post 消費数などが返り、予算管理・アラート・高消費エンドポイントの特定・レポートに使える。

### Enterprise

高ボリューム・専用サポート・カスタムレート制限などは Enterprise 問い合わせ。  
**Pay-per-usage は Post 読み取り 月 200 万件が上限**。それを超える場合は Enterprise を検討。
