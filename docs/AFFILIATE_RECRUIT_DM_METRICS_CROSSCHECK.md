# リクルートDM 数字の整合性（X API ダッシュボード vs Vercel ログ）

## 対象ラン（例: 2026-02-26 04:00 UTC・EN）

| 出所 | 指標 | 値 |
|------|------|-----|
| X API ダッシュボード | DM Interaction Create | 3 |
| X API ダッシュボード | Read | 6 |
| Vercel ログ | 試行した候補数 | 8 |
| Vercel ログ | 送信成功 | 3 |
| Vercel ログ | 403（DM拒否） | 5 |

---

## 1. DM Interaction Create と 送信成功

| ダッシュボード | ログ | 整合 |
|----------------|------|------|
| **Create: 3** | **送信成功: 3** | ✅ 一致 |

- X API は「DM が実際に作成された」回数だけを Create としてカウントする。
- 403 は「送信できなかった」ため **Create にカウントされない**。
- よって **Create = 送信成功** で一致する。

---

## 2. 試行 8 と 成功 3 ＋ 403 の 5

| ログ | 内訳 | 整合 |
|------|------|------|
| 試行 8 | 成功 3 ＋ 403 が 5 ＝ 8 | ✅ 一致 |

- 1 候補につき 1 回 POST（DM 送信試行）。
- 8 候補 → 8 回試行。うち 3 が Create、5 が 403。
- 403 の 5 回は **クレジット消費（Create）には入らない**。

---

## 3. Read: 6 の内訳

Read は **DM 送信以外の読み取り系 API** の回数。

リクルートランで行っている読み取り系は主に次のとおり。

| 処理 | API | 想定回数（EN・今回のラン） |
|------|-----|----------------------------|
| 候補検索 | GET `/2/tweets/search/recent` | 複数回（クエリ数 × ページ数） |

- `buildSearchQueries("en")` で複数クエリ（キーワードをバケット分割）。
- 各クエリごとに `pagesPerBucket`（デフォルト 3）までページ取得。
- **Read: 6** は、例えば「検索 2 クエリ × 3 ページ」や「検索 3 クエリ × 2 ページ」など、**合計 6 回の search/recent 呼び出し**で説明できる。

（ユーザー取得が search の expansions で完結している場合は、追加の Read はほぼ発生しない想定。）

---

## 4. まとめ

| 項目 | 結論 |
|------|------|
| Create 3 vs 送信成功 3 | ✅ 一致（403 は Create に含まれない） |
| 試行 8 = 3 + 5 | ✅ 一致 |
| Read 6 | ✅ 候補検索（tweet search）の呼び出し回数と整合 |

**403 はクレジット（DM Interaction Create）にカウントされていない。**  
Read 6 は検索 API の呼び出し回数と整合する。
