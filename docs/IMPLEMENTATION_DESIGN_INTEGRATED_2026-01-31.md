## 1. ビジネス・戦略の前提

- **ターゲット**: トレード依存症のトレーダー（「絶望的な最適化者」）。
- **無料版（Minimal Version）**: **試薬** — 反応を見る・トリアージする入口。治すわけではない。
- **有料版（Regular Briefing）**: **処方箋** — 深い分析・シグナル・心理サポートとしての「処方」。
- **設計意図**: トレードを止めさせる（完治させる）のではなく、**我々の配信がないと回らなくなる**状態をつくる。依存先を「市場の衝動」から「Trap Defence の配信」に寄せる。
- **今後の展開**: Xアルゴリズムと人間の深層心理をハッキングして**チートプログラム**を実装する流れに特化する。

→ 実装・Cron・コンテンツはすべてこの設計に従う。

### 1.1 収益最大化のための優先順位（判断基準）

| 優先度 | 観点 | 具体例 |
|--------|------|--------|
| 1 | **処方箋の転換・継続** | Whop CTA 優先、Saved Loss 表示で「配信の価値」を可視化、無料→有料の導線強化。 |
| 2 | **試薬の質と量** | 100/15min 厳守でアカウント保護、ピーク時間・レキシコンでエンゲージメント最大化、間欠強化で通知ON維持。 |
| 3 | **計測と改善** | 試薬の反応・処方箋の開封・継続を Cron/配信と紐づけ、収益に効く施策から手を入れる。 |
| 4 | **運用効率** | タイムアウト・エラー削減で配信ロスを防ぐ。新機能は収益インパクトが大きいものから。 |

→ 迷ったら「どれが収益に直結するか」で優先する。

### 1.2 逆算思考とチートコード実装（運用原則）

- **常に収益最大化からの逆算で考える**  
  施策・機能・文言は「処方箋の転換・継続」「試薬の質と量」にどう効くかで評価する。収益に繋がらないものは後回しにする。

- **Grok（Xアルゴリズム解析）と Gemini（深層心理解析）を入力とする**  
  Grok は「Xの穴・最適化ポイント」、Gemini は「何を・どう出して心理を動かすか」を出す。この2つを統合した戦略がコンテンツ・スケジュール・フォーマットの根拠になる。

- **実装側がチートコードに落とし込む**  
  解析結果を「プロンプト任せ」にせず、**コードで保証できる部分は必ず実装する**（質問CTA保証、100/15min厳守、レキシコン注入、Saved Loss表示、ジッター・間欠強化など）。Grok/Geminiの知見 → 仕様 → チートコードとして実装、という一本の流れで進める。

→ まとめ: **収益最大化（逆算） → Grok×Gemini の知見 → チートコード実装**。解析は入力、実装は出力。

### 1.3 データ駆動のチートコード改善ループ

- **現状のコードを走らせてデータを取る**  
  Cron・配信・投稿はそのまま回し、Vercel ログ・Whop・X の反応・開封率・転換率など、取れるデータを蓄積する。

- **そのデータをチートコードのヒントにする**  
  実データ（どの時間帯で反応が良いか、どの文言で CVR が上がるか、どこで離脱するかなど）を、次の Grok×Gemini への問いやチートコードの仕様に反映する。解析・実装は「データありき」で更新していく。

- **ループの形**  
  **現状コード稼働 → データ取得 → データをヒントにチートコード改善（Grok×Gemini の入力にも利用） → 実装 → また稼働・計測**。計測・ログ・KPI の紐づけ（§4.2 のギャップ）は、このループを回すために重要になる。

→ まとめ: データが次のチートコードのヒントになる。まずは走らせて取りつつ、改善する。

## 2. Grok と Gemini の役割分担

| モデル | 得意 | 苦手 |
|--------|------|------|
| **Grok** | Xアルゴリズム解析。チート術（穴・最適化ポイント）の発見。 | 攻略のためのコンテンツ戦略。 |
| **Gemini** | 攻略のためのコンテンツ戦略（何を・どう出して勝つか）。深層心理の言語化。 | アルゴリズムの細かい穴掘り。 |

→ 実装では「Grok = アルゴリズム・チート術」「Gemini = コンテンツ戦略」と役割を分けて使う。  
→ 両者の出力を統合したうえで、**§1.2 の逆算＋チートコード実装**に従い、コードで保証できる形に落とす。

### 2.1 GPT-5-mini の脇役（最適化案）

有料レポートの主役を **Gemini（SoSoValue風記事）＋ Grok（推論チェーン・X×オンチェーン乖離）** にした場合、**GPT-5-mini は脇役**に限定し、主役と被らないようにする。

| 脇役の役割 | 内容 | 主役との棲み分け |
|------------|------|------------------|
| **1. データ整形・要約** | 生の CryptoQuant ＋ 価格 ＋ センチメントを、Grok と Gemini が使いやすい形に**事実だけ**要約。分析や解釈は書かせない。 | 主役＝Grok（推論）・Gemini（記事）。GPT-mini＝入力の正規化のみ。 |
| **2. 緊急トリガー（軽量ゲート）** | 非定期枠で「異常かどうか」を短いプロンプトで判定。Yes なら Grok 推論＋緊急配信、No ならスキップ。 | 今の analyzeCryptoQuantData を「閾値越え → 1文で異常度だけ聞く」に縮小。深い分析は Grok に任せる。 |
| **3. フォールバック** | Gemini または Grok が失敗・タイムアウトしたとき、GPT-mini で「本日の数値サマリ 1 文」だけ生成。主役の代わりはしない。 | 主役が落ちたときの安全網。 |
| **4. 多言語 1 文サマリ（任意）** | Gemini が生成した記事の「要約 1 文」を GPT-mini で他言語に。主コンテンツは Gemini、翻訳・要約だけ GPT-mini。 | 主役＝Gemini（記事）。GPT-mini＝ローカライズ・要約のユーティリティ。 |

→ **やらないこと**: 長文の「Mental Trainer 風分析」「CryptoQuant 詳細解説」「シグナル・推論」は Gemini と Grok に集約。GPT-mini は**短い・構造化・判定のみ**に限定し、コストとレイテンシを抑える。

## 3. 現状実装（コードで保証しているもの）

### 3.1 投稿パイプラインで確実に効いているもの

| 項目 | 場所 | 内容 |
|------|------|------|
| **100/15min 厳守** | postTracker + x-quote-repost | getPostCountInLast15Min、count+targetCount>100 でスキップ。 |
| **ピークマップ・人数** | optimization.js, influencerStrategy.js | getPeakMapForHour、getInfluencerCountForLang で 8/9/20–22 時など制限。 |
| **ジッター** | x-quote-repost.js | 0–15 分ランダム遅延を実行前に適用。 |
| **Whop チェックアウト優先** | x-quote-repost, x-post-minimal-version, x-post-free-report | minimalCheckoutUrl を優先、未設定時のみ t.me。 |
| **140 文字時の CTA/リンク保持** | services/x/client.js (postQuoteTweet) | 切り詰め時に `?` と URL を残す。 |

### 3.2 監査対応で追加したコード保証（2026-01-31）

| 項目 | 実装内容 |
|------|----------|
| **質問 CTA のコード保証** | `ensureQuestionCTA(quoteText, lang)`。投稿前に `?` が末尾 50 文字以内にない場合はデフォルト質問 CTA を付与し、140 文字で再切り詰め。 |
| **スレッド戦略の接続** | `getThreadStrategy(lang)` を x-quote-repost で参照。メイン引用リポスト成功後、replyCount > 0 のとき `replyToTweet` で最大 replyCount 回までリプライ投稿。 |
| **最適化スキップ条件の緩和** | `MIN_REMAINING_TIME_FOR_OPTIMIZATION` を 30 秒→**15 秒**に変更。optimizationStrategy が null になりにくい。 |
| **optimizationStrategy のコード利用** | テキスト生成の戻り値を `{ quoteText, optimizationStrategy }` に変更。投稿前に format に「メディア・画像」等が含まれる場合の分岐を追加（のちに引用リポスト画像付与は廃止）。 |

### 3.3 方針で廃止したもの

- **引用リポスト画像付与**: QUOTE_REPOST_IMAGE_URL / getQuoteRepostMediaId は廃止（NanoBanana/Veo 不安定）。無料版・有料版のテキスト引用のみで運用。

## 4. CronJobs と設計の対応

### 4.1 試薬／処方箋との対応

| Cron | スケジュール | 設計上の役割 |
|------|--------------|--------------|
| `/api/cron` | 15分ごと | **試薬＋処方箋** — TG 無料版・有料版の定期/緊急配信。「15分でFOMO」の核。 |
| `/api/x-post-minimal-version-cron` | 0,7,12,15,23時 UTC | **試薬** — X 無料版スレッド（Hook / Quick Reads / Psych / Poll+CTA）。 |
| `/api/x-post-free-report` | 4,10,17,19時 30分 UTC | **試薬** — X 無料レポート。 |
| `/api/x-quote-repost-*` | 6分ごと等（言語分散） | **試薬への誘導** — 引用リポスト → Whop 無料版 or t.me。 |
| `/api/vsl1-post`, `/api/vsl2-*`, `vsl1-reminder` | 各スケジュール | ファネル。 |
| `/api/promo-stock-monitor` | 15分ごと | 運用。 |

### 4.2 ギャップ（まだ不十分な点）

1. 処方箋の「確定時刻」が Cron 設計に明示されていない。  
2. 試薬→処方箋の遷移が Cron の実行順・時間帯として意図的に組まれていない。  
3. 「配信がないといけなくなる」時刻の固定が弱い。  
4. 戦略に沿ったKPI（試薬の反応・処方箋の開封・継続）が Cron/配信ログと紐づいていない。

### 4.3 方針（2026-01-31）

現状の仕組みも相当理詰めで実装してきた経緯があるため、**まずは様子を見る**。ギャップの解消や Cron 設計の見直しは、観察結果を踏まえてから検討する。

## 5. 次のフェーズ戦略（Grok × Gemini 統合）

### 5.1 共通認識

- **コア・ナラティブ**: 「依存症治療」から**「市場攻略のためのハッキングツール（共犯関係）」**へ。ユーザーは「選ばれしハッカー」と定義。
- **Save と Dwell Time の最重視**: いいね稼ぎや低品質な自作自演は排除。「保存必須」と感じさせる高密度な視覚情報でアルゴリズムの「有益性」評価をハック。
- **役割分担**: 無料（試薬）= 不安の可視化・損失回避の提示・ドーパミン（期待）。有料（処方箋）= 思考停止の正当化・具体的な行動指示・セロトニン（安心）。

### 5.2 優先事項（Priorities）

| # | 項目 | 心理側 | アルゴリズム側 |
|---|------|--------|----------------|
| 1 | **Saved Loss の儀式化** | 「損しなかった額」を強調し命綱としての依存度を高める。 | 無料で「回避成功」チャートを Quote、有料スレッドへ誘導。リプライで「回避できたか？」でエンゲージメント。 |
| 2 | **保存特化型スレッド** | 「今保存しないと二度と見られない裏技」として相関図・チェックリスト等を投下。 | 言語別ピークで 2–4 ツイートスレッド。滞在時間・Save 数で For You 露出最大化。 |
| 3 | **独自言語の最適化** | 3–5 語の強力な独自用語で帰属意識・排他性を高める。 | 難解になりすぎずバイラルを阻害しない範囲。 |
| 4 | **間欠的強化（ランダム・アラート）** | 不定期な緊急回避シグナルで常に通知 ON にさせる緊張状態。 | 定時 15 分とは異なるタイミングで鮮度（Recency）を維持。 |

### 5.3 直近で着手すべきアクション

1. **「保存ベイト（Save Bait）」アセットの制作** — 攻略チャート・市場相関図のテンプレート。画像内に情報を詰め込み滞在時間・保存率を向上。  
2. **「Saved Loss」レポートのフロー構築** — 損失回避額を可視化し、無料で拡散→有料で解説する投稿フォーマット（画像+コピー）をテンプレート化。  
3. **15 分儀式の微調整** — Cron に ±2〜5 分ジッター、投稿冒頭に 5 秒以内のオーディオ・ビジュアルイントロで条件反射を強化。

| 項目 | 実装内容 |
