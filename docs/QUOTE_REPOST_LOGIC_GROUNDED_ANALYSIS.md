# 引用リポストロジック：根拠の整理と再分析指針

**状況**: 6言語×8コピー、クリック後はVSL/LPでコンバージョン見込みがあるが、トラフィックが壊滅。条件が複雑化し、根拠のない仮説でロジックが定義されている可能性がある。もう一度分析する必要がある。

**問い**: 「本当に伸びている 2〜7分の投稿」を狙うべきか？ 何が事実で何が仮説か？

---

## 1. 現状の「条件」一覧と根拠の有無

| 条件・パラメータ | 根拠の種類 | 備考 |
|------------------|-------------|------|
| **2〜7分ウィンドウ**（120〜420秒） | **仮説・コードの固定値** | PQT_TARGET_QUALITY_RESEARCH.md では「2〜7分は**極端に狭く**、アルゴリズムは**60分**までが重要という知見とずれる」と**否定的**に書かれている。それでもコードは 2〜7 分をデフォルトのまま採用し、in2_7Window が 1 件でもあると**それ以外を捨てている**。X 公式や論文の出典はない。 |
| **Rising window（2分〜7分 or 60分）** | **一般的知見（要検証）** | 「初動 60 分が重要」は研究 doc に書いてあるが、X の公式ドキュメントや公開アルゴの記述ではない。実データで「投稿年齢」と our_impressions の相関を取っていない。 |
| **Engagement velocity**（経過時間あたりの engagement） | **一般的知見（要検証）** | 「初動の速度が重要」はソーシャルアルゴの共通理解に近いが、**当リポの引用リポストで「velocity が高い引用元を引くと our_impressions が高い」かは未検証**。 |
| **Topic fit**（BTC/ETH/トレード/リスク等キーワード） | **設計意図** | Trap Defence のメッセージと合う話題を引くという**意図**。成約・クリックとの相関は**実データで取っていない**。 |
| **Copy fit**（コピーが刺さる引用元キーワード） | **設計意図** | コピーテーマと引用元の文言を揃えようという**意図**。インプレ・CTR との相関は**未検証**。 |
| **Fisherman**（hype キーワード + engagement ≥ 500） | **ヒューリスティック** | 「煽りっぽい伸び投稿」を検出するためのキーワード＋閾値。**私たちの引用が伸びるか**との相関は未検証。研究 doc では「私たちの付加価値と必ずしも一致しない」と指摘済み。 |
| **中央値フィルタ**（score ≥ median×1.2） | **相対フィルタ** | 「その検索結果の中ではまあまあエンゲージされている」という相対的な足切り。**絶対的な根拠はない**。 |
| **品質スコアの重み**（velocity 30% + alg 30% + topic 20% + copyFit 20% + hype） | **仮説** | 各要素の重みは**恣意的**。実データで回帰や A/B していない。 |
| **MIN_VELOCITY / MIN_TOPIC_FIT / MIN_COPY_FIT** | **仮説** | 「閾値以上だけ採用するとインプレが伸びる」は**未検証**。 |
| **検索窓 30 分** | **運用上の設定** | 短くすると件数が減る・長いと古い投稿が混ざる、というトレードオフ。**何分が our_impressions と相関するかは未検証**。 |
| **1 run = 1 言語** | **実装都合** | 6 言語を round-robin。**言語別のインプレ差を実データで見てから振り方を決めているわけではない**。 |

**結論**: **「2〜7分」「velocity」「topic/copy fit の重み」「Fisherman」など、多くの条件は「一般的な考え」や「設計意図」であり、当リポの buzzweave_post_log で「その条件を満たすと our_impressions / our_clicks / our_subs が高い」とは検証していない。**

## 2. 矛盾：研究 doc とコード

- **PQT_TARGET_QUALITY_RESEARCH.md**  
  - 「2–7 分だけだと**外れる投稿が多い**」「初動 **60 分**が重要」と明記。  
  - 「2–30 分」または「2–60 分」を rising とし、2–7 分は「最優先にしてもよい」と提案。

- **コード（buzzWeaveEngine.js）**  
  - 品質スコア選定**でない**とき: **in2_7Window が 1 件でもあると、2〜7 分のスロットだけに絞る**（それ以外を捨てる）。  
  - 品質スコア選定時: rising は 2分〜BUZZWEAVE_RISING_WINDOW_MAX_SEC（デフォルト 420 = 7分）。60分にするには明示的に 3600 を設定する必要がある。

→ **研究で「2〜7分は狭すぎ」と書いてあるのに、コードは 2〜7 分を強く効かせたまま。仮説に基づく条件が積み重なり、根拠の再検証が追いついていない。**

---

## 3. 何を「事実」として扱うか

- **事実になりうるもの**:  
  - buzzweave_post_log に溜まる **our_impressions, our_clicks, our_subs** と、**slot_lang, cluster_label, 引用元の engagement_score, 投稿時刻（UTC 時間帯）** など、**ログに存在する項目**だけ。
- **仮説のまま扱うもの**:  
  - 「2〜7分が最適」「velocity が高い引用元を引くべき」「copy fit で足切りすべき」など。**実データで条件別のインプレ・クリック・成約を出してから**採用・緩和を決める。

---

## 4. 再分析でやること（優先）

1. **実データの集計**  
   - `scripts/analyze-our-pqt-buzz.js` で、**直近 N 日**の buzzweave_post_log を集計。  
   - **slot_lang / UTC時間帯 / cluster_label** など、**今ログにある項目**で、our_impressions・our_clicks・our_subs の平均・合計を出す。  
   - 「どの条件でインプレ・クリック・成約が出ているか」を**数値で見る**。ここまでが根拠。

2. **「2〜7分」の検証**  
   - ログに**引用元の投稿時刻**（または投稿年齢）があれば、**引用元の年齢（例: 0–7分 / 7–30分 / 30分〜）** でインプレ・クリックを集計。  
   - もし「2〜7分」のときのインプレが**他より明らかに高い**なら、その窓を活かす根拠になる。**差がなければ「2〜7分に絞る」ロジックは緩和してよい**（例: rising を 2–60 分に広げる、または窓で絞らない）。

3. **条件の削減**  
   - 実データで**差が出ていない**条件（例: topic_fit の閾値、copy_fit の閾値、2〜7分の厳格な絞り）は、**一旦オフまたは緩める**。  
   - 「トラフィックを壊滅させない」を最優先に、**投稿本数とシンプルな選定**（例: 検索で取った候補を engagement 降順で cap まで）でベースラインを出し、そこから「何を足すと効くか」をデータで試す。

4. **狙うべきターゲットの問い直し**  
   - 「本当に伸びている 2〜7分の投稿」は、**仮説**。  
   - 検証するまで「2〜7分を狙うべき」とは言い切れない。**データで「引用元の年齢と our_impressions の関係」を出してから**、窓の幅・優先度を決める。

---

## 5. シンプルなベースライン案（複雑化を戻す）

- **最小ロジック**:  
  - 検索（既存クエリ・窓）→ 候補取得 → **engagement 降順**（または impressionScore 降順）→ **cap まで採用**。  
  - 2〜7分での**強制絞り込み**をやめる。rising を使うなら **2–60 分**など広めにして、その中でソートだけする。  
- **閾値の見直し**:  
  - MIN_VELOCITY / MIN_TOPIC_FIT / MIN_COPY_FIT は **0 のまま**（足切りしない）か、分析で「明らかに効く」と分かってから導入する。  
- **目的**:  
  - 「条件が多すぎてトラフィックが死んでいる」を避け、**まず本数を出してログを溜め、そのログで「何が効くか」だけを根拠に足していく**。

### シンプル選定をデフォルトに（実装済み）

- **デフォルト**: **シンプル選定**。候補を **engagement 降順**で並べ、**cap まで**採用。Fisherman 必須・品質スコア・2〜7分での絞り込みは使わない。  
- **BUZZWEAVE_SIMPLE_SELECTION=false** にすると従来モード（Fisherman または品質スコア選定）に戻る。

### 窓で「捨てない」をデフォルトに（実装済み）

- **デフォルト**: 2〜7分（または rising）**以外を捨てない**。スロットは窓内を優先してソートするだけ。  
- **BUZZWEAVE_SKIP_WINDOW_NARROWING=false** で従来の「窓内だけに絞る」に戻す。シンプル選定時は常に窓で捨てない。

### 中央値フィルタをスキップするオプション（実装済み）

- **BUZZWEAVE_SKIP_MEDIAN_FILTER=true** にすると、中央値フィルタ（median×1.2 以上）を使わず、**engagement 降順で上から maxCandidates まで**を候補にする。候補数を増やしたいときに使う。シンプル選定デフォルト時は中央値もスキップ済み。

### 6言語圏の時間に合わせた言語切り替え（実装済み）

- **言語をクエリで指定しないとき**、**UTC 時刻**で言語を選ぶ（デフォルト）。
  - UTC 0–3 → ja（日本時間帯）
  - UTC 4–7 → ko
  - UTC 8–11 → en
  - UTC 12–15 → es
  - UTC 16–19 → pt
  - UTC 20–23 → ar
- Cron が `0 0,3,6,9,12,15,18,21 * * *`（UTC）なら、0・3 時→ja、6 時→ko、9 時→en、12・15 時→es、18 時→pt、21 時→ar となり、各言語がその圏の活動時間に近い UTC で run される。
- **BUZZWEAVE_LANG_BY_UTC=false** で従来の「分単位 round-robin」に戻す。`?lang=en` でクエリ指定すれば常にその言語。

---

## 6. まとめ

- **複雑化**: 2〜7分・velocity・topic/copy fit・Fisherman・品質スコア・複数閾値が積み重なっているが、**当リポの実データで「その条件がインプレ・成約と相関する」と示していない**。  
- **根拠のない仮説**: 「本当に伸びている 2〜7分の投稿を狙う」は**仮説**。研究 doc ですら「2〜7分は狭すぎ」と書いてある。狙うべきかは**分析で引用元年齢×our_impressions を出してから**決める。  
- **再分析**: `analyze-our-pqt-buzz.js` とログにある項目で条件別のインプレ・クリック・成約を出し、**差がつく条件だけ**残す。差がつかない条件は緩めるか外す。  
- **トラフィック**: 壊滅を防ぐには、**条件をいったん減らし、ベースライン（engagement 降順・窓の緩和）で本数を出してデータを取る**のが優先。
