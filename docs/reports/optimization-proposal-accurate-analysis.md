## 📋 重要な前提条件の再確認

### X APIレート制限の正確な理解

**`POST /2/tweets`（引用リポストも含む）**:
- **Per User (OAuth 1.0a)**: **100/15min**（15分窓、15分ごとにリセット）
- **Per App (Bearer Token)**: **10,000/24hrs**（24時間窓）

**重要な誤解の訂正**:
- ❌ 誤解: 「100/15min = 理論上9,600/24時間」→ これは単純計算で、実際の運用では**15分ごとにリセット**される
- ✅ 正解: **15分ごとに100投稿まで可能**だが、スパム判定を避けるため**均等分散が重要**
- ✅ 実際の運用: 短時間集中も可能だが、**自然さを優先**して分散する必要がある

**参考**: [X API Rate Limits](https://docs.x.com/x-api/fundamentals/rate-limits)

### 我々の戦略の深い部分の理解

#### 1. インフルエンサーストック管理の詳細

**現在の実装**:
- **Grok発掘**: `discoverInfluencersForQuoteRepost` が各インフルエンサーの**最新ホットツイート（tweetId）**を取得
- **ストック保存**: Vercel KVに保存（**24時間TTL**、**1人1ツイート**）
- **更新頻度**: 24時間ごと（または手動更新）
- **各インフルエンサー**: **1つのtweetId**を持つ（最新のホットツイート）

**重要な制約**:
- ストックは「1人1ツイート」なので、同じインフルエンサーに複数回投稿するには**新しいツイートが必要**
- ストック更新時に新しいツイートが追加されれば、同じインフルエンサーに複数回投稿可能
- しかし、**24時間TTL**なので、更新頻度が低いと枯渇しやすい

#### 2. ローテーション機能の詳細

**現在の実装**:
- **今日の投稿済みリスト**: 今日既に投稿したインフルエンサーを除外
- **柔軟なローテーション**: 利用可能なインフルエンサーが不足 → **投稿済みも含める（ローテーションリセット）**
- **問題点**: リセットにより**同一インフルエンサー偏重**が発生しやすい

#### 3. 重複投稿防止の詳細

**現在の実装**:
- **tweetIdベース**: 過去24時間の同じtweetIdへの投稿を防止
- **新しいツイート**: 新しいツイートが投稿されれば、同じインフルエンサーに複数回投稿可能
- **制約**: tweetIdが変わらない限り、同じインフルエンサーに複数回投稿できない

#### 4. タイミングチェックの詳細

**現在の実装**:
- **緩和された制限**: 60分以内であれば投稿を許可
- **ピーク時間**: UTC 0,1,20,21,22であれば60分を超えても投稿を許可
- **問題点**: 「最低間隔」ではなく「許可条件」なので、**短時間連投のリスク**がある

## 🎯 正確な最適化目標

### X APIレート制限との整合性

**Per User制限（OAuth 1.0a）**:
- **100/15min**: 15分ごとに100投稿まで可能
- **理論上24時間最大**: 100 × 96 = 9,600投稿/日
- **実際の運用**: スパム判定を避けるため、**均等分散**が重要

**Per App制限（Bearer Token）**:
- **10,000/24hrs**: 24時間で10,000投稿まで可能
- **実際の運用**: Per User制限の方が厳しいので、こちらがボトルネックになることは少ない

### スパム判定リスクの正確な評価

**X APIのスパム判定アルゴリズム**（公開仕様なし）:
- **同一インフルエンサーへの連続投稿**: 高いリスク
- **短時間集中**: 高いリスク
- **同一パターン文面**: 高いリスク
- **自然な分散**: 低いリスク

**我々の戦略のリスク**:
- **現状**: 「1人1ツイート」ストック + 「枯渇時リセット」→ **同一インフルエンサー偏重**のリスク
- **対策**: クールダウン + リセット禁止 + 分散投稿

## 🔧 正確なP0改善案

### 1. インフルエンサー単位クールダウン（8時間）

**目的**: 同一インフルエンサーへの短時間連投を防止

**実装の詳細**:
- KVに `x:influencer_last_posted:{lang}:{username}` を保存（TTL: 24時間）
- `selectInfluencersWithRotation` でクールダウンをチェック
- **クールダウン時間: 8時間**（環境変数 `X_INFLUENCER_COOLDOWN_HOURS` で設定可能）

**重要な考慮事項**:
- **ストック更新頻度**: 24時間TTLなので、8時間クールダウンでも**新しいツイートがあれば投稿可能**
- **実効的な投稿数**: 1日3回（0時、8時、16時）のストック更新があれば、同じインフルエンサーに3回投稿可能

### 2. 枯渇時リセット禁止

**目的**: 同一インフルエンサー偏重を防止

**実装の詳細**:
- 候補不足時はリセットせず、**利用可能な分だけ返す**
- または、**別言語へフォールバック**（`api/x-quote-repost.js` で実装）

**重要な考慮事項**:
- **ストック更新頻度**: 24時間TTLなので、更新頻度を上げることで枯渇を防げる
- **層別更新**: 上位20人は2〜4時間ごと、残り50人は12〜24時間ごと（GPT-5.2推奨）

### 3. 15分窓レートリミッタ

**目的**: X APIレート制限（100/15min）を遵守し、自然さを優先

**実装の詳細**:
- 15分単位の投稿数カウンタを追加
- **環境変数 `X_MAX_POSTS_PER_15M` で設定可能（デフォルト: 10）**
- **重要**: X APIの100/15min制限に対して、**安全マージン**を取る（10/15min = 10%使用）

**重要な考慮事項**:
- **自然さ優先**: 10/15min = 1時間あたり40投稿 = 24時間で960投稿（理論上）
- **実際の運用**: スパム判定を避けるため、**均等分散**が重要

### 4. 構造化ログ

**目的**: 投稿決定理由を記録して最適化可能にする

**実装の詳細**:
- 投稿決定時の理由（スコア、クールダウン、重複判定など）を構造化ログで記録
- Vercel KVまたはログファイルに保存

### 5. 日次上限の一元化確認

**目的**: ハードコード50が残っていないか確認

**実装の詳細**:
- 既に環境変数 `X_MAX_DAILY_POSTS` に統一されているか確認
- ハードコード50が残っていないか検索

## 📊 正確な環境変数の推奨値

```bash
# 日次投稿数上限（安全運用開始: 40-60、安定後: 60-90）

# 15分窓の投稿数上限（自然さ優先、X API 100/15minの10%使用）

X_MAX_POSTS_PER_15M=10

# インフルエンサー単位のクールダウン時間（時間）
# 重要: 8時間 = 1日3回のストック更新があれば、同じインフルエンサーに3回投稿可能

# 1人あたりの日次上限（オプション、将来的に実装）
X_PER_INFLUENCER_DAILY_CAP=2

# グローバル最小投稿間隔（分、ジッター込みで5-15分）
X_GLOBAL_MIN_GAP_MINUTES=8
```

## ⚠️ 正確なリスク評価

### スパム判定リスク

**現状**:
- **40〜60/日**: 中リスク（枯渇時リセットにより同一インフルエンサー偏重）
- **100+/日**: 高リスク（現状のままでは危険）

**改善後**:
- **40〜60/日**: 低リスク（クールダウンと分散により）
- **60〜90/日**: 低〜中リスク（指標を監視しながら）

**対策**:
- クールダウン（8時間）
- 分散投稿（15分窓レートリミッタ）
- 文面多様化
- 枯渇時スキップ
- バックオフ（429/403エラー時）

### X APIレート制限超過リスク

**現状**:
- **低リスク**: 90/日は余裕（Per User 100/15min = 理論上9,600/日）

**改善後**:
- **低リスク**: 15分窓レートリミッタ（10/15min）により、安全マージンを確保

**対策**:
- 15分窓レートリミッタ（10/15min）
- 日次上限（60/日）
- 時間単位上限（既存）

### コスト増加リスク

**現状**:
- **中リスク**: 投稿数増 = 引用5cr + 生成10cr

**改善後**:
- **中リスク**: 投稿数増加によりコスト増加

**対策**:
- AI生成は反応が良い枠だけ、他は軽量テンプレ
- ストック更新頻度の最適化（層別更新）
