# Upstash Redis（Vercel KV）の制約と考慮事項
**作成日時**: 2026-01-27T04:35:00.000Z
**目的**: Upstash Redisの制約を踏まえた実装の最適化と将来の移行計画

---

## 現在の状況

### Vercel KV → Upstash Redis移行
- **Vercel KVは廃止**: 2024年12月に廃止され、既存のKVストアは自動的にUpstash Redisに移行
- **`@vercel/kv`パッケージ**: 非推奨だが、既存プロジェクトでは引き続き動作
- **推奨パッケージ**: 新規プロジェクトでは`@upstash/redis`を使用

### 現在のプラン（Free Tier）
- **Commands**: 2.5K / 500K per month（0.5%使用）
- **Storage**: 352KB / 256MB（0.1%使用）
- **Bandwidth**: 0B / 50GB（0%使用）
- **Cost**: $0.00

## 実装への影響

### 1. 現在の実装（`@vercel/kv`使用）

**使用箇所:**
- `services/x/influencerRotation.js`: ローテーション管理、8時間クールダウン
- `services/x/postTracker.js`: 投稿履歴追跡
- `services/free-users/kv-storage.js`: 無料版ユーザー管理
- `services/cryptoquant/client.js`: キャッシュ

**動作状況:**
- ✅ 現在は正常に動作
- ⚠️ 将来的には`@upstash/redis`への移行を検討

### 2. ロックキー実装（`nx`オプション）

**現在の実装:**
- `acquireLock`関数で`nx`オプションを試行
- サポートされていない場合は代替実装（再チェック方式）を使用

**Upstash Redisの確認事項:**
- Upstash Redisは標準的なRedisコマンドをサポート
- `SET NX EX`コマンドは動作するはずだが、`@vercel/kv`パッケージのAPIがサポートしているかは不明
- 現在の実装は代替方式も含めて動作する設計

## 制約とリスク分析

### Free Tierの制約

**Commands制限（500K/month）:**
- **現在の使用量**: 2.5K/month（0.5%）
- **180-300投稿/日の戦略での見積もり**:
  - 1投稿あたりのKV操作: 約10-15回（getLastPostedAt, isInCooldown, markLastPostedAt, markInfluencerPosted, 日次カウント等）
  - 1日あたり: 180-300投稿 × 10-15操作 = 1,800-4,500操作
  - 1ヶ月あたり: 54,000-135,000操作
- **結論**: Free Tierの制限内（500K/month）で動作可能

**Storage制限（256MB）:**
- **現在の使用量**: 352KB（0.1%）
- **見積もり**:
  - 8時間クールダウンキー: 70インフルエンサー × 6言語 × 24時間 = 約10,080キー
  - 日次投稿済みリスト: 6言語 × 365日 = 2,190キー
  - 各キーのサイズ: 約100-500バイト
  - **合計**: 約1-5MB（256MBの2-20%）
- **結論**: Storage制限内で十分に動作可能

**Bandwidth制限（50GB/month）:**
- **現在の使用量**: 0B
- **見積もり**: KV操作は軽量なため、制限内で動作可能

### スケーリング時の考慮事項

**180-300投稿/日を超える場合:**
- Commands使用量が増加するため、監視が必要
- Pay as You Goプラン（$0.2 / 100K commands）への移行を検討
- 1ヶ月あたり135K操作 = 約$0.27（非常に低コスト）

**Storage増加時:**
- 256MBを超える場合は、Fixed 1GBプラン（$20/month）への移行を検討

## 改善提案

### 1. KV操作の最適化（P1）

**現状:**
- 各投稿で複数のKV操作が発生
- ロック取得時のリトライで追加のKV操作が発生

**改善案:**
- バッチ処理: 複数のインフルエンサーのクールダウンチェックをまとめて取得
- キャッシュ: 同一実行内での重複取得を避ける

### 2. 監視とアラート（P1）

**実装推奨:**
- KV操作数の監視（日次/月次）
- Storage使用量の監視
- 制限に近づいた場合のアラート

### 3. `@upstash/redis`への移行検討（P2）

**移行のメリット:**
- 標準的なRedisコマンドの完全サポート（`SET NX EX`など）
- より詳細なエラーハンドリング
- 将来のメンテナンス継続性

**移行のタイミング:**
- `@vercel/kv`が完全に動作しなくなった時
- 新しい機能で標準的なRedisコマンドが必要になった時

**移行の影響:**
- コードの変更が必要（`require('@vercel/kv')` → `require('@upstash/redis')`）
- 環境変数の変更（`KV_URL` → `UPSTASH_REDIS_REST_URL`等）
- 既存のデータはそのまま使用可能（同じUpstash Redisインスタンス）

## 実装の確認事項

### 1. `nx`オプションの動作確認

**確認方法:**
- 実際の環境で`acquireLock`関数をテスト
- `nx`オプションがサポートされている場合は、より効率的な実装に改善可能

**現在の実装:**
- `nx`オプションを試行し、エラー時は代替実装を使用
- これにより、どちらの場合でも動作する

### 2. ロックキーのTTL設定

**現在の実装:**
- ロックキーのTTL: 10秒
- 最大リトライ: 10回（100ms間隔）
- 最大待機時間: 1秒

**考慮事項:**
- ロック取得に失敗した場合でも処理を続行（可用性優先）
- デッドロック回避のため、TTLを適切に設定
