# Cron Jobs問題原因分析レポート（GPT-5.2-2025-12-11）
**作成日時**: 2026-01-27T02:09:56.678Z
**モデル**: gpt-5.2-2025-12-11

---

## 実行サマリー

- **Cron自体は定期実行されている**（`api/x-quote-repost` 277回呼ばれている）が、**“処理が進むべき本体ロジック”にほぼ到達していない**。
- `x-quote-repost` の実行フローは **「インフルエンサー取得完了(18件)」以降が全滅**（ローテーション選択0 / ループ開始0 / X API呼び出し0）。
- 直接の停止要因として、`api/x-quote-repost.js` 内で **`Assignment to constant variable` が発生して処理が落ちている**可能性が高い（9件、特定言語で再現）。
- 別系統で `api/cron` 側は **GPT API 400 がリトライ後も失敗**（19件）。これはX投稿0件の主因ではないが、Cron全体の健全性を落としている。

---

## 根本原因の分析

### 根本原因A（最重要）: `x-quote-repost` が “言語ごとの処理” に入れていない／入っても途中で落ちている
ログ上、`x-quote-repost` は 277回叩かれているのに **言語処理開始が4回しかない**ため、以下のいずれかが強く疑われます。

1) **言語ループの手前で早期returnしている**
- 例: 認証/シークレットチェック、環境変数不足、実行時間帯制限、Vercel Cronのヘッダ検証失敗などで “200を返して終了” している
- ただし、エラーが9件出ているので「常に手前でreturn」ではなく、**条件によっては中に入る**構造のはず

2) **言語リストが空/想定外になっている**
- 例: `LANGS` が env 依存で空、設定JSONのロード失敗、フィルタ条件で全言語が弾かれている
- 結果として「エンドポイント呼び出しだけ増えるが、言語処理開始が増えない」

3) **言語処理に入ったケースでは、後段で例外により落ちている**
- 実際に `Assignment to constant variable` が出ている言語（ko/ar/pt-br/es）では、**処理が途中で例外終了**している

> 結論: **「言語処理に入れない構造的問題」＋「入った場合も const再代入でクラッシュ」**の二重障害の可能性が高いです。

---

### 根本原因B: X API投稿が0件の直接原因は「インフルエンサーループに到達していない」こと
フロー上、X APIの手前ログが0件なので、**X APIの認証やクレジット以前の問題**です。  
到達していない理由はログから2つに絞れます。

- **(B1) ローテーション選択結果が0件**  
  つまり「インフルエンサー取得後に、投稿対象の選定（ローテーション）が1件も確定していない」か、「確定ログの直前で落ちている」。

- **(B2) `Assignment to constant variable` でローテーション処理中に例外終了**  
  レポート上で該当箇所が `api/x-quote-repost.js` の **549行目/576行目**と特定されており、ここがローテーションやフィルタリングの再代入地点である可能性が高い。

> 結論: **X API 0件は“X APIが悪い”のではなく、選定・ループ開始前に処理が止まっているため**です。

---

### 根本原因C: `Assignment to constant variable` の理由（ほぼ確定）
このエラーはNode/JSで **`const` 変数に再代入した**ときに発生します。典型例:

```js
const influencers = await getInfluencers()
influencers = influencers.filter(...) // ← ここで落ちる
```

レポートの推奨（`const influencers` → `let influencers` 等）は筋が通っています。  
そして「修正がデプロイされていない可能性」とある通り、**ローカルで直したつもりでもVercelの本番が古いビルドを動かしている**ケースが現実的です（ブランチ違い/環境変数のビルドキャッシュ/デプロイ対象の取り違え）。

さらに、発生言語が偏っている点から、以下も疑えます。

- 特定言語だけ `influencers` を再構成する分岐がある（例: 言語別の除外ルール、地域別の候補数制限など）
- その分岐で `const` 再代入が発火している

> 結論: **コード上のバグ（const再代入）＋本番に修正が反映されていない/特定分岐でのみ発火**が根因です。

---

### 根本原因D: GPT APIエラー（OpenAI API error: 400）の理由
400は「リクエストが不正」です。ログに `isTimeout:true` が付いているのは不自然で、**エラーハンドリングが“400もタイムアウト扱い”に誤分類**している可能性があります（根本原因の切り分けを困難にしている）。

400の典型原因は以下です（頻度順）:

1) **モデル名/エンドポイント不一致**
- 例: Responses API/Chat Completions APIの呼び分けミス
- 例: 廃止/権限のないモデルを指定

2) **入力パラメータ不正**
- `messages` の形式不正、`tools` 定義不正、`response_format` 不正、`max_tokens`/`temperature` 範囲外など

3) **コンテンツサイズ超過**
- 送っているデータ（CryptoQuant分析用データ）が大きすぎて制限超過

4) **APIキーやプロジェクト設定の問題**  
通常は401/403になりやすいが、SDKやゲートウェイ次第で400に見えることもある

> 結論: GPTエラーは `api/cron` 側の別問題で、**「リクエスト仕様不整合（モデル/パラメータ/サイズ）」が主因**。加えて **エラー分類が誤っており調査を阻害**しています。

## 実行フローの問題点（どこで止まっているか）

提示されたフローから、停止点は明確です。

- **停止点1（構造的停止）**:  
  `エンドポイント呼び出し 277 → 言語処理開始 4`  
  → **273回は言語処理に入る前に終了**している  
  ここは「ガード節（早期return）」か「言語リスト空」か「条件でスキップ」のどれか。

- **停止点2（致命的停止）**:  
  `インフルエンサー取得完了 18 → ローテーション選択 0`  
  → ここは **例外で落ちている（const再代入）**か、**選定条件が厳しすぎて常に0件**。

- **停止点3（結果）**:  
  `インフルエンサーループ開始 0 → X API呼び出し 0`  
  → 当然、投稿処理に到達しない

重要なのは、**「インフルエンサー取得完了」が「言語処理開始」より多い**という点です。  
通常は `言語処理開始 >= インフルエンサー取得開始/完了` になるはずなので、以下のどれかが起きています。

- ログ集計のキーが混在している（同じ文言が別経路で出ている）
- 例外時にリトライ/並列実行でログ順序が崩れている
- 「言語処理開始」ログが一部の経路でしか出ていない（ログ欠落）

> つまり、**ログ設計自体が“フロー観測”に不十分**で、真の停止点が見えにくくなっています（後述の予防策で改善）。

## エラーパターンの分析

### 1) `Assignment to constant variable`（9件、言語偏りあり）
- **発生言語**: ko/ar/pt-br/es  
- **示唆**:
  - 言語別分岐でのみ `const` 再代入が起きる
  - あるいは対象言語のみ「インフルエンサー候補が0/少ない」などの特殊ケースになり、配列の再構築処理が走る
- **結果**:
  - その言語の処理が例外終了
  - ローテーション選択ログやループ開始ログが出ない
  - X API 0件に直結

### 2) GPT API error: 400（19件）
- **prefix**: `analyzeCryptoQuantData`
- **特徴**:
  - 「リトライ後も失敗」→ 恒常的なリクエスト不正
  - `isTimeout:true` は誤分類の疑い（400はタイムアウトではない）
- **結果**:
  - `api/cron` の成功率低下（33 errors）
  - ただし `x-quote-repost` のX投稿0件の直接原因ではない（系統が違う）

## 修正方法の提案（優先度順）

### P0: `Assignment to constant variable` を確実に潰し、本番へ確実に反映
**目的**: ローテーション選択〜ループ開始に到達させる

1) 該当行（549/576付近）で **再代入が必要なら `let` に変更**
- 例:
  - `const influencers` → `let influencers`
  - `const selectedInfluencers` → `let selectedInfluencers`
- もしくは **再代入しない書き方へ変更**（推奨）
  - `const filtered = influencers.filter(...)` のように別変数にする

2) **Vercel本番に修正が載っていることを機械的に確認**
- VercelのDeploymentごとに `git commit sha` をログに出す（起動時に出力）
- エンドポイントで `version`（commit hash）を返す簡易ヘルスを用意
- 「修正したブランチ」ではなく「本番が参照するブランチ」にマージされているか確認

3) 例外で全体が止まらないようにする
- 言語単位・インフルエンサー単位で `try/catch` し、**1件失敗しても次に進む**
- 失敗時は「どのステップで落ちたか」を必ずログ化（後述）

**検証方法**
- 手動で `api/x-quote-repost?lang=es&dryRun=1` のような形で1言語だけ実行（可能なら）
- ログに `ローテーション選択結果` と `インフルエンサーループ開始` が出ること
- 最低1回は `X API呼び出し試行` が出ること（dryRunなら擬似ログでOK）

---

### P1: 「言語処理開始が4件しかない」原因を潰す（ガード節/スキップ条件の可視化）
**目的**: 277回呼ばれているのに中身が動かない問題を解消

1) エンドポイント冒頭に以下を必ずログ出力
- 実行モード（cron/manual）
- 実行対象言語一覧（配列の中身）
- 早期returnする条件と、その判定結果
  - 例: `CRON_SECRET ok?`, `enabled?`, `timeWindow ok?`, `alreadyRan?` など

2) 早期return時も「成功(200)」ではなく、**理由を含んだレスポンス**にする
- 例: `200 { skipped: true, reason: "outside_time_window" }`
- 可能なら `207 Multi-Status` 的に言語ごとの結果を返す（運用が楽）

3) 言語処理開始ログが「一部経路でしか出ない」なら、ログを統一
- `postQuoteRepostsForLang(lang)` の冒頭で必ず出す
- 呼び出し側でも `starting lang loop: langs=[...]` を出す

**検証方法**
- 1回の実行で `langs=[...]` が期待通り出ること
- 277回のうち大半がスキップなら、スキップ理由の内訳がログで集計できること

---

### P2: ローテーション選択が0件になるロジックを点検（データ条件/閾値）
**目的**: 例外が消えても「常に0件選ばれる」状態を防ぐ

確認観点（よくある原因）:
- インフルエンサー候補が0件（DB/外部取得失敗、フィルタで全除外）
- ローテーションの状態管理（前回投稿時刻、クールダウン）が厳しすぎる
- 「言語別の最小インプレッション」等の閾値が高すぎる
- 取得完了ログは出るが、中身が空配列（`length=0`）でも完了ログが出ている

対策:
- `rotation selection` の直前に
  - 候補数、除外理由の内訳（cooldown除外◯件、impression不足◯件…）をログ
- 0件の場合は「0件になった理由」を必ず出す（沈黙しない）

**検証方法**
- 0件の場合でも「なぜ0件か」がログ1回で分かること
- 閾値を一時的に緩めてでもX API呼び出しまで通ることを確認

---

### P3: GPT API 400 を解消（`api/cron` の安定化）
**目的**: Cron全体の失敗率を下げ、運用を安定化

1) 400のレスポンスボディを必ず記録（秘匿情報をマスクして）
- OpenAIは400時に「どのフィールドが不正か」を返すことが多い  
- 現状は `OpenAI API error: 400` だけで原因が追えない

2) リクエスト仕様を点検
- 使用API（Responses / ChatCompletions）とpayloadが一致しているか
- `model` が有効か
- `messages` 形式が正しいか
- 入力データのサイズ（トークン数）を事前に見積もる／長すぎる場合は要約してから投げる

3) エラー分類を修正
- 400を `isTimeout:true` にしない
- `status`, `code`, `type` を構造化してログ

**検証方法**
- 同一入力で再実行し、400が解消すること
- 失敗するなら「どのフィールドが原因か」がログから判別できること

## 予防策の提案（再発防止）

### 1) フロー観測可能なログ設計（構造化＋相関ID）
- すべての `x-quote-repost` 実行に `runId` を付与し、全ログに出す
- ステップログを **必ず同じキーで** 出す（例: `step=rotation_selected count=...`）
- 例外時には `step` と `lang` と `influencerId` を必ず付与

### 2) “スキップ” を成功に埋めない
- 「実行はされたが何もしなかった」を成功扱いにすると、今回のように気づけない
- 指標を分ける:
  - `invoked`
  - `skipped`（理由別）
  - `processed_langs`
  - `posted_count`

### 3) 監視・アラート
最低限アラートにすべきKPI:
- `x-quote-repost`: **X API呼び出し数が一定時間0**
- `rotation_selected == 0` が連続（例: 3回連続）
- 例外 `Assignment to constant variable` の発生（即時）
- `api/cron`: GPT 400 が一定回数/時間を超えたら通知

Vercel + 外部（Datadog/Sentry/Logtail等）で
- エラー集約（スタックトレース付き）
- リリースバージョン（commit）単位でのエラー増加検知

### 4) デプロイの取り違え防止
- 本番起動時に `GIT_SHA` を必ずログ
- `/_meta` エンドポイントで `sha`, `buildTime`, `env` を返す
- “修正したのに直らない” を即座に潰せる
